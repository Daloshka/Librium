# Librium: как устроен перехватывающий прокси

[← Назад к индексу](../README.ru.md) · Далее: [Сеть](network.md), [Настройка прокси](proxy-setup.md)

Заметки для выстраивания понимания и написания точных промптов агентам.
Цель первой версии: Windows 10, Rust.
macOS поддерживается начиная с версии 0.5.x; примеры ниже приведены для Windows.

## Картина целиком

### Прослушивание порта

Прокси один раз открывает слушающий сокет и дальше в цикле принимает
соединения. Каждое принятое соединение уходит в отдельную асинхронную
задачу (tokio::spawn), а цикл сразу возвращается ждать следующее.

    ┌──────────────────────────── Librium (процесс) ────────────────────────────┐
    │                                                                           │
    │   TcpListener::bind("127.0.0.1:8080")                                     │
    │              │                                                            │
    │              ▼                                                            │
    │   ┌─── loop { listener.accept().await } ───┐                              │
    │   │                                        │                              │
    │   │   соединение #1 ──▶ tokio::spawn ──▶ [задача 1: handle(conn)]         │
    │   │   соединение #2 ──▶ tokio::spawn ──▶ [задача 2: handle(conn)]         │
    │   │   соединение #3 ──▶ tokio::spawn ──▶ [задача 3: handle(conn)]         │
    │   │        ...                             ...                            │
    │   └────────────────────────────────────────┘                              │
    │                                                                           │
    │   Задачи независимы. Одно зависшее соединение не блокирует остальные.     │
    │   Общее состояние (история, настройки, кэш сертификатов) передаётся       │
    │   в каждую задачу через Arc<State>.                                       │
    └───────────────────────────────────────────────────────────────────────────┘
              ▲               ▲               ▲
              │               │               │        каждое соединение это
         браузер          браузер            curl      своя TCP-четвёрка:
       вкладка A        вкладка B                      127.0.0.1:51234 → 127.0.0.1:8080
                                                       127.0.0.1:51235 → 127.0.0.1:8080
                                                       ...

Браузер обычно открывает к прокси несколько соединений сразу (6 на хост
в HTTP/1.1) и переиспользует их, поэтому задач в любой момент десятки.

### Один HTTPS-запрос через прокси

Что происходит внутри одной задачи handle(conn), когда браузер запрашивает
https://example.com/. Время идёт сверху вниз.

    Браузер                    Librium (задача)                    example.com:443
       │                            │                                    │
       │  TCP handshake             │                                    │
       │◀──────────────────────────▶│                                    │
       │                            │                                    │
       │  CONNECT example.com:443   │                                    │
       │───────────────────────────▶│  читает хост из первой строки      │
       │                            │                                    │
       │  200 Connection Established│                                    │
       │◀───────────────────────────│                                    │
       │                            │                                    │
       │  TLS ClientHello (SNI)     │                                    │
       │───────────────────────────▶│  сертификат для example.com:       │
       │                            │  кэш → или rcgen + подпись CA      │
       │  TLS ServerHello + cert    │                                    │
       │◀───────────────────────────│                                    │
       │  ...handshake...           │                                    │
       │◀──────────────────────────▶│  ── DNS example.com ──▶            │
       │                            │  ── TCP handshake ──────────────▶  │
       │                            │  ── TLS handshake (rustls-клиент) ▶│
       │                            │                                    │
       │  ═══ TLS-туннель A ═══     │      ═══ TLS-туннель B ═══         │
       │                            │                                    │
       │  GET / HTTP/1.1            │                                    │
       │  Host: example.com         │                                    │
       │═══════════════════════════▶│  расшифровал (поток A)             │
       │                            │  сохранил сырые байты запроса      │
       │                            │  [Intercept? ждёт решения из UI]   │
       │                            │  зашифровал (поток B) ════════════▶│
       │                            │                                    │
       │                            │◀════════════ HTTP/1.1 200 OK ══════│
       │                            │  расшифровал (поток B)             │
       │                            │  сохранил ответ, записал в историю │
       │◀═══════════════════════════│  зашифровал (поток A)              │
       │                            │                                    │
       │  следующий запрос по тому же туннелю (keep-alive) ...           │

    ──▶  открытый текст       ═══▶  внутри TLS

Ключевые точки:

- Задача держит **два сокета**: к браузеру и к серверу, и **два TLS-состояния**:
  серверное (rustls ServerConnection, выдаёт себя за example.com) и клиентское
  (rustls ClientConnection, честно подключается к серверу).
- Между ними прокси видит открытый HTTP и здесь живёт вся логика:
  история, перехват, правила, поиск.
- Сертификат для хоста генерируется один раз и кэшируется, иначе каждый
  handshake будет стоить миллисекунды на подпись.
- Обычный HTTP без CONNECT проходит тот же путь, только без TLS-обёрток.

## Как трафик попадает в прокси

Инструмент вроде Caido не «ловит» трафик сам. Он слушает TCP-порт на localhost,
например 127.0.0.1:8080, а браузер или приложение добровольно отправляют запросы
туда. Это называется explicit proxy. Ничего специфичного для Windows здесь нет:
прокси задаётся в настройках системы, а браузер берёт его оттуда либо
настраивается отдельно через расширение вроде FoxyProxy.

Драйверы, WinDivert и перехват на уровне сети для первой версии не нужны,
это отдельная и намного более сложная тема.

Ядро программы: обычный TCP-сервер на порту, говорящий по протоколу HTTP-прокси.

## Что происходит с одним запросом

### Обычный HTTP

Браузер открывает соединение к прокси и присылает запрос с полным URL
в первой строке:

    GET http://example.com/path HTTP/1.1

Прокси читает его, открывает своё соединение к example.com, пересылает запрос,
получает ответ и отдаёт его браузеру. Всё в открытом виде.

### HTTPS, ключевая часть

Браузер не может отправить прокси зашифрованный запрос, поэтому сначала
присылает команду:

    CONNECT example.com:443 HTTP/1.1

Это просьба «создай туннель до этого хоста». Честный прокси отвечает
`200 Connection Established` и дальше слепо гоняет байты в обе стороны.

Перехватывающий прокси делает подмену (MITM):

1. Отвечает браузеру `200`, как обычный прокси.
2. Внутри туннеля сам начинает TLS-рукопожатие с браузером, выдавая себя
   за example.com. Для этого на лету генерирует сертификат на имя example.com
   и подписывает его своим корневым сертификатом (CA).
3. Отдельно открывает настоящее TLS-соединение к настоящему example.com.
4. Теперь у прокси два расшифрованных потока, и он видит запросы и ответы
   как обычный текст.

Браузер согласится на подмену только если корневой сертификат прокси добавлен
в доверенные. На Windows 10 это хранилище «Доверенные корневые центры
сертификации»:

    certutil -addstore Root ca.crt

Firefox использует своё хранилище, туда добавлять отдельно.
Это единственный по-настоящему Windows-специфичный шаг во всём проекте.

Нюансы:

- Имя хоста для сертификата берётся из строки CONNECT или из SNI, поля
  в начале TLS-рукопожатия, где браузер сообщает целевой хост.
- Сертификаты нужно кэшировать, чтобы не генерировать заново на каждое соединение.

## Что происходит внутри программы дальше

После расшифровки поток проходит через конвейер:

- **Парсер HTTP.** Разбирает байты на метод, путь, заголовки, тело.
  Критично хранить сырые байты, а не только разобранную структуру,
  потому что нормализация прячет атаки.
- **Перехват (Intercept).** Если включён, запрос ставится на паузу,
  показывается пользователю, тот правит его и нажимает «отправить» или
  «сбросить». Технически это канал между сетевым потоком и UI:
  сетевая задача ждёт ответа от UI.
- **История.** Каждая пара запрос и ответ пишется в SQLite с метаданными:
  время, хост, статус, размер.
- **Replay.** Запрос из истории отправляется заново отдельным HTTP-клиентом,
  минуя прокси.
- **UI.** Отдельный процесс или окно, общается с ядром через API
  (у Caido это GraphQL поверх HTTP и WebSocket). Разделение позволяет ядру
  работать без окна.

## Словарь для промптов на Rust

- **tokio** — асинхронный runtime, на нём всё сетевое.
- **hyper** — HTTP-библиотека низкого уровня, режимы сервера и клиента.
- **rustls** — TLS-реализация; **tokio-rustls** её асинхронная обёртка.
- **rcgen** — генерация сертификатов и CA.
- **httparse** — низкоуровневый парсер HTTP без нормализации.
- **rusqlite** / **sqlx** — работа с SQLite.
- **hudsucker** — готовый MITM-прокси на этих компонентах; основа или учебный пример.
- **Tauri** — десктопное окно с веб-интерфейсом.

### Пример чёткого промпта на первый шаг

> Сделай на Rust с tokio и hyper HTTP-прокси, слушающий 127.0.0.1:8080.
> Для обычных запросов проксируй их на целевой хост и логируй метод, URL
> и статус. Для CONNECT делай MITM: генерируй сертификат на хост через rcgen,
> подписывай нашим CA из файла ca.pem, устанавливай TLS с клиентом через
> tokio-rustls, к серверу подключайся тоже через rustls. Сырые байты запроса
> и ответа сохраняй без изменений.

## План первых шагов

1. Создать проект (cargo).
2. Сгенерировать CA.
3. Установить CA в Windows.
4. Поднять прокси, который пока только логирует хосты.
5. Посмотреть трафик браузера через него.

## Как Librium устроен сейчас

Выше — общая картина перехватывающего прокси. Ниже — что именно реализовано
в этом репозитории, чтобы промпты и правки опирались на реальный код.

### Процессы

- **Ядро** (`src/`, Rust, один процесс): прокси на hudsucker/hyper с MITM по
  локальному CA (`ca.rs`), захват (`capture.rs`), SQLite-хранилище
  (`storage.rs`), HTTP API для интерфейса (`main.rs`, axum) и WebSocket-запись
  (`websocket.rs`). Слушает только `127.0.0.1`: прокси на `LIBRIUM_PROXY_PORT`
  (8080), API и встроенный интерфейс на `LIBRIUM_UI_PORT` (3000).
- **Electron** (`desktop/`): запускает ядро, показывает `ui/` в изолированном
  рендерере (`sandbox`, `contextIsolation`, без `nodeIntegration`) и через
  `preload.cjs` даёт ему узкий мост IPC. Всё, что требует файлов, сети от имени
  приложения или системных инструментов, живёт в `main.cjs`: сохранение
  файлов, экспорт HAR (`har.cjs`), повтор и составление запроса с нуля (`replay.cjs`; id 0 — нет захвата, всё из правки), правила файлом (`export-rules`/`import-rules`, общая проверка `rulesPayload`), распаковка
  тел (`decode.cjs`), установка CA (`ca-install.cjs`), ретранслятор для
  телефона (`mobile.cjs`).
- **Интерфейс** (`ui/`): один `app.js` без сборки; общие модули `filters.js`
  (правила, синтаксис поиска) и `i18n.js` используются и рендерером, и
  main-процессом; `suggest.js` (подсказки в строке поиска), `curl.js` (разбор
  вставленной команды cURL) и `params.js` живут только в рендерере. Тот же интерфейс ядро отдаёт по `http://127.0.0.1:3000/`
  без Electron — тогда недоступны только функции моста.

### Путь одного обмена

1. `Capture::handle_request` создаёт `Exchange` в памяти (`History.rows`,
   отсортированы по id) и оборачивает тело запроса в `observe()`:
   кадры считаются и копируются в превью (64 КиБ, для медиа до 32 МиБ),
   а `Completion` отмечает конец потока, ошибку или обрыв.
2. `handle_response` записывает статус, заголовки, версию и тип содержимого и
   так же оборачивает тело ответа. Обмен «завершён» (`finished`), когда обе
   стороны закончились; ошибка одной стороны не мешает другой течь дальше.
3. Раз в полсекунды `flush_shared` забирает из истории изменённые строки и
   очередь WebSocket-кадров вместе с соединением к SQLite, пишет их **без
   мьютекса** и возвращает результат: при неудаче строки снова помечаются
   изменёнными, очередь встаёт на место, а в `/api/state` появляется `error`.
   Пока обмен течёт, на диск идёт только превью; полное тело — после конца.
4. Интерфейс раз в секунду спрашивает `/api/state` (ревизия, размер на диске,
   ошибка, число задержанных перехватом, счётчики активных правил `tweaks`) и
   перечитывает страницу, деталь и кадры только при новой ревизии.
   Чтение идёт через отдельное read-only соединение к той же базе (WAL),
   поэтому запросы интерфейса не тормозят захват.

Между «запрос пришёл» и «запрос записан» стоят две необязательные ступени.
Правки заголовков (`Settings.rewrites`, `settings.json`; хост и шаблон пути) применяются к
подходящему хосту прямо в `handle_request`, поэтому история показывает то,
что реально ушло; `response_rewrites` — так же в `handle_response`, после
перехвата и до записи, так что в истории заголовки, которые получил клиент; `delays` — искусственная
задержка ответа там же (первая подходящая строка по хосту и шаблону пути), она входит в записанную длительность. Моки (`Settings.mocks`) проверяются в `handle_request`
сразу после игнорируемых хостов (порядок: мок → правки заголовков → флаг записи или игнор → перехват → запись; игнорируемый хост — это «не записывать», правила для него действуют): первый подходящий по хосту, пути (шаблон с `?` сверяется с путём и query) и методу отвечает сам,
обмен записывается как обычный (статус, тип, тело, заголовок `x-librium-mock`), к серверу
запрос не уходит и под перехват не попадает; задержка `delays` и правки ответов `response_rewrites` действуют и на мок. Перехват (`src/intercept.rs`) — состояние только в памяти:
если правила включены и подходят хост, метод и путь (пустой список — любой), тело запроса буферизуется (известная
длина, до 8 МиБ; поток или больше — проходит без задержки), запрос встаёт в
очередь `State.queue` с `oneshot`-каналом и ждёт решения интерфейса до
десяти минут; `Decision` заранее разбирается в `Edit` (метод, адрес, код,
заголовки, тело), так что на стороне прокси ошибок уже не бывает. Ответы
задерживаются так же в `handle_response`, до записи статуса — тела
неизвестной длины буферизуются через `Limited`, сверх лимита ответ
заканчивается ошибкой `TOO_LARGE`. Отброшенное или несостоявшееся
превращается в обмен с ошибкой и ответ 502 клиенту; клиент, ушедший во время
ожидания, вычищается из очереди по закрытому каналу.

### Хранилище

`history.sqlite3`, WAL, `synchronous=NORMAL`. Таблица `traffic`: колонки для
фильтров и сортировок (`method`, `host`, `path`, `status`, `size`, `kind`,
индексы по ним), `search` (текст для свободного поиска), `body` (распакованный
текст тел для `body:`), `headers` (строки «имя: значение» обеих сторон для `header:`; условие `frame:` — EXISTS по `ws_messages`), `summary` и `detail` (JSON для списка и инспектора),
`pending` (обмен ещё мог завершиться, когда программу остановили).
`ws_sessions` и `ws_messages` — WebSocket. `metadata` — `next_id` (id не
переиспользуются после очистки) и `marked_id` (до какого id строки проверены
при старте). Очистка делает `VACUUM`, завершение — чекпоинт WAL.

### API ядра

Все пути `/api/*` требуют заголовок `x-librium-token` (токен вписан в
страницу) и проверку `Host`. `GET /api/state`, `GET /api/traffic-page?q=`
(поиск: `query`, `method`, `status`, `traffic_type`, `rules`, `sort`,
`order`, `offset`, `limit`, `before`), `GET /api/traffic/{id}`,
`GET /api/traffic/{id}/ws?before=|after=`, `DELETE /api/traffic` (всё),
`DELETE /api/traffic/{id}` (один обмен), `PATCH /api/traffic/{id}` (звезда и заметка,
колонки `starred`/`note` плюс те же поля в документах), `DELETE /api/traffic-page?q=` (всё, что
подходит под поиск), `POST /api/import` (обмены из HAR: получают новые id,
кадры WebSocket — в очередь как при захвате), `GET /api/traffic-stats?q=` (агрегаты по
тому же поиску: итоги, перцентили задержки, коды, методы, хосты), `GET|PUT /api/recording` (флаг записи в памяти: выключен — правила действуют, история и перехват нет), `GET|PUT /api/intercept`
(правила перехвата: enabled, hosts, methods, path, responses) и `POST /api/intercept/{id}` (решение: forward с
правками метода/адреса/кода/заголовков/тела или drop; задержанное живёт только в памяти), `POST /api/storage-flush`, `POST /api/shutdown`,
`GET /api/ca`, `GET /api/info`, `GET|PUT /api/settings` (игнорируемые хосты и правки заголовков
запросов `rewrites`, ответов `response_rewrites`, задержки `delays` и моки `mocks`; PUT принимает частичный объект; `settings.json` в каталоге данных).

### Проверки

`cargo test` (в том числе HTTP-тест API и прокси-тест на живых сокетах),
`npm run test:ui` (jsdom: рендерер с мостом и без, HAR, установка CA),
`python3 scripts/export-source.py --check`. Electron-проверки в `scripts/`
запускаются с `LIBRIUM_HEADLESS=1` и не показывают окон.
