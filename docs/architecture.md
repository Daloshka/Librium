# Librium: как устроен перехватывающий прокси

[← Назад к индексу](../README.md) · Далее: [Сеть](network.md), [Настройка прокси](proxy-setup.md)

Заметки для выстраивания понимания и написания точных промптов агентам.
Цель первой версии: Windows 10, Rust.

В текущем ядре рукопожатие WebSocket выполняется через Hyper, а пересылка кадров — через `fastwebsockets` в `src/ws_transport.rs`. Раздельные читатели двух направлений отключают автоматические PONG / CLOSE, чтобы не добавлять ответы к трафику конечных сторон. Проверка масок и заголовков кадров выполняется до разбора; фрагменты передаются сразу, а для истории отдельно собирается сообщение с ограниченным префиксом 64 КиБ. HTTP upgrade сохраняет уже прочитанные Hyper байты первого кадра. Для WSS используется rustls с проверкой WebPKI; отказ HTTP возвращается с исходным телом. Подробности и ограничения — в [руководстве по трафику приложений](custom-traffic.md).

Поиск WebSocket по одному соединению и по всему архиву использует общий `PreparedWsFilter` в `src/storage.rs`: одинаковые типизированные условия и аннотации найденных диапазонов. `POST /api/ws-archive-search` выполняется в отдельном read-only снимке SQLite через общий семафор WS-чтений (два рабочих потока). Промежуточная материализация содержит только ID совпадений, полные сообщения читаются для страницы из 101 записи, а в ответ попадают не более 100 коротких превью. Верхняя граница по ID сообщения и курсор `before` сохраняют порядок страниц во время захвата. Полный пакет читается существующим API по ID соединения и сообщения.

`GET /api/traffic/{id}/ws/{message_id}/context` читает до пяти соседей с каждой стороны исходного сообщения в том же соединении. Существование и принадлежность исходного ID проверяются с соединением и записью истории; обе выборки выполняются в одном read-only снимке через `read_ws`. Индекс `(exchange_id,id)` позволяет найти соседей без разбора всей сессии. API контекста и общего поиска используют один помощник коротких превью; полный пакет и экспорт не получают этих сокращений.

Сопоставление JSON-RPC находится в `src/jsonrpc.rs` и `Store::ws_jsonrpc_related`. Разбор использует `RawValue` для ID и вложенных данных, отвергает дубли ключей объектов протокола, сохраняет позиции элементов пакета. Десятичная нормализация ID выполняет точную работу с коэффициентом и строковой экспонентой без float и ограничения диапазоном целого процессора. Один запрос ищет пару одного выбранного элемента во всей записи соединения через read-only снимок и семафор WS-чтений. Число кандидатов считается полностью, а выдача ограничена 20 ссылками каждого вида. ID повторного использования не разбиваются на предполагаемые пары; `null` и уведомления остаются без автоматической связи.

Форматы `jsonrpc_method` и `jsonrpc_id` используют тот же разбор `src/jsonrpc.rs`, что и сопоставление пар. Условие JSON-RPC выполняется до проверки пустой строки, чтобы пустой запрос выбирал только корректные элементы протокола, а не все сообщения. SQLite-функция кэширует подготовленный ID через auxdata; тип и точный десятичный ключ не пересоздаются для каждой строки. Пагинация применяется после структурной фильтрации. Аннотация `rpc_entries` добавляется только к результатам поиска и переносит индекс первого совпадения в инспектор; строки архива и экспорт не изменяются.

`GET /api/traffic/{id}/ws-profile` классифицирует признаки сохранённого содержимого через `src/ws_profile.rs`. Запись читается последовательно в read-only снимке, Base64 декодируется один раз на прикладное сообщение; проверенные текстовые данные передаются общим разборщикам JSON-RPC / CDP без повторного декодирования. В памяти остаются счётчики фиксированного набора групп и до двух примеров каждого направления на группу. Полезная нагрузка в ответ не переносится, сжатие не запускается. Проверки заголовков gzip / zlib служат только подсказкой для явной ограниченной распаковки.

Общий `json_object::Object` хранит исходные `RawValue` и отвергает дубли декодированных имён на одном уровне объекта. Его используют CDP и JSON-RPC для конверта и `error`; вложенные прикладные данные остаются нетронутыми. В интерфейсе режимы RPC отдельно проверяют исходные имена, поскольку обычный `JSON.parse` сохраняет последнее значение дубля. Сканер после проверки синтаксиса пропускает вложенные контейнеры итеративно и не выбирает значение за пользователя. Векторы в `scripts/rpc-unique-vectors.json` проверяются Rust и JavaScript.

Формат поиска `content_kind` использует `ws_profile::Kind` и тот же `classify`, что и сводка содержимого. SQLite-функция кэширует выбранную группу через auxdata, классифицирует исходные записи и фильтрует их до пагинации; счётчик совпадает с группой сводки в одном снимке. Тип кадра и направление остаются независимыми условиями. `content_kind` и индекс первого конверта JSON-RPC добавляются лишь к результатам, без изменения архива. Клиентские названия, виды и кодеки берутся из одного списка метаданных сводки; переходы через обычный и общий поиск используют общий обработчик открытия с защитой версии инспектора.

## Картина целиком

Явная распаковка сохранённых BINARY-сообщений находится в `src/inflate.rs` и вызывается отдельным API-запросом. Она не участвует в пересылке кадров: ядро читает ограниченный диапазон из истории, отпускает блокировку и выполняет распаковку в рабочем потоке. Оба размера ограничены 64 КиБ, результат не записывается обратно в историю. Это позволяет исследовать сжатую полезную нагрузку без изменения наблюдаемого обмена.

### Прослушивание порта

Прокси один раз открывает слушающий сокет и дальше в цикле принимает
соединения. Каждое принятое соединение уходит в отдельную асинхронную
задачу (tokio::spawn), а цикл сразу возвращается ждать следующее.

    ┌──────────────────────────── Librium (процесс) ────────────────────────────┐
    │                                                                           │
    │   TcpListener::bind("127.0.0.1:8080")                                     │
    │              │                                                            │
    │              ▼                                                            │
    │   ┌─── loop { listener.accept().await } ───┐                              │
    │   │                                        │                              │
    │   │   соединение #1 ──▶ tokio::spawn ──▶ [задача 1: handle(conn)]         │
    │   │   соединение #2 ──▶ tokio::spawn ──▶ [задача 2: handle(conn)]         │
    │   │   соединение #3 ──▶ tokio::spawn ──▶ [задача 3: handle(conn)]         │
    │   │        ...                             ...                            │
    │   └────────────────────────────────────────┘                              │
    │                                                                           │
    │   Задачи независимы. Одно зависшее соединение не блокирует остальные.     │
    │   Общее состояние (история, настройки, кэш сертификатов) передаётся       │
    │   в каждую задачу через Arc<State>.                                       │
    └───────────────────────────────────────────────────────────────────────────┘
              ▲               ▲               ▲
              │               │               │        каждое соединение это
         браузер          браузер            curl      своя TCP-четвёрка:
       вкладка A        вкладка B                      127.0.0.1:51234 → 127.0.0.1:8080
                                                       127.0.0.1:51235 → 127.0.0.1:8080
                                                       ...

Браузер обычно открывает к прокси несколько соединений сразу (6 на хост
в HTTP/1.1) и переиспользует их, поэтому задач в любой момент десятки.

### Один HTTPS-запрос через прокси

Что происходит внутри одной задачи handle(conn), когда браузер запрашивает
https://example.com/. Время идёт сверху вниз.

    Браузер                    Librium (задача)                    example.com:443
       │                            │                                    │
       │  TCP handshake             │                                    │
       │◀──────────────────────────▶│                                    │
       │                            │                                    │
       │  CONNECT example.com:443   │                                    │
       │───────────────────────────▶│  читает хост из первой строки      │
       │                            │                                    │
       │  200 Connection Established│                                    │
       │◀───────────────────────────│                                    │
       │                            │                                    │
       │  TLS ClientHello (SNI)     │                                    │
       │───────────────────────────▶│  сертификат для example.com:       │
       │                            │  кэш → или rcgen + подпись CA      │
       │  TLS ServerHello + cert    │                                    │
       │◀───────────────────────────│                                    │
       │  ...handshake...           │                                    │
       │◀──────────────────────────▶│  ── DNS example.com ──▶            │
       │                            │  ── TCP handshake ──────────────▶  │
       │                            │  ── TLS handshake (rustls-клиент) ▶│
       │                            │                                    │
       │  ═══ TLS-туннель A ═══     │      ═══ TLS-туннель B ═══         │
       │                            │                                    │
       │  GET / HTTP/1.1            │                                    │
       │  Host: example.com         │                                    │
       │═══════════════════════════▶│  расшифровал (поток A)             │
       │                            │  сохранил сырые байты запроса      │
       │                            │  [Intercept? ждёт решения из UI]   │
       │                            │  зашифровал (поток B) ════════════▶│
       │                            │                                    │
       │                            │◀════════════ HTTP/1.1 200 OK ══════│
       │                            │  расшифровал (поток B)             │
       │                            │  сохранил ответ, записал в историю │
       │◀═══════════════════════════│  зашифровал (поток A)              │
       │                            │                                    │
       │  следующий запрос по тому же туннелю (keep-alive) ...           │

    ──▶  открытый текст       ═══▶  внутри TLS

Ключевые точки:

- Задача держит **два сокета**: к браузеру и к серверу, и **два TLS-состояния**:
  серверное (rustls ServerConnection, выдаёт себя за example.com) и клиентское
  (rustls ClientConnection, честно подключается к серверу).
- Между ними прокси видит открытый HTTP и здесь живёт вся логика:
  история, перехват, правила, поиск.
- Сертификат для хоста генерируется один раз и кэшируется, иначе каждый
  handshake будет стоить миллисекунды на подпись.
- Обычный HTTP без CONNECT проходит тот же путь, только без TLS-обёрток.

## Как трафик попадает в прокси

Инструмент вроде Caido не «ловит» трафик сам. Он слушает TCP-порт на localhost,
например 127.0.0.1:8080, а браузер или приложение добровольно отправляют запросы
туда. Это называется explicit proxy. Ничего специфичного для Windows здесь нет:
прокси задаётся в настройках системы, а браузер берёт его оттуда либо
настраивается отдельно через расширение вроде FoxyProxy.

Драйверы, WinDivert и перехват на уровне сети для первой версии не нужны,
это отдельная и намного более сложная тема.

Ядро программы: обычный TCP-сервер на порту, говорящий по протоколу HTTP-прокси.

## Что происходит с одним запросом

### Обычный HTTP

Браузер открывает соединение к прокси и присылает запрос с полным URL
в первой строке:

    GET http://example.com/path HTTP/1.1

Прокси читает его, открывает своё соединение к example.com, пересылает запрос,
получает ответ и отдаёт его браузеру. Всё в открытом виде.

### HTTPS, ключевая часть

Браузер не может отправить прокси зашифрованный запрос, поэтому сначала
присылает команду:

    CONNECT example.com:443 HTTP/1.1

Это просьба «создай туннель до этого хоста». Честный прокси отвечает
`200 Connection Established` и дальше слепо гоняет байты в обе стороны.

Перехватывающий прокси делает подмену (MITM):

1. Отвечает браузеру `200`, как обычный прокси.
2. Внутри туннеля сам начинает TLS-рукопожатие с браузером, выдавая себя
   за example.com. Для этого на лету генерирует сертификат на имя example.com
   и подписывает его своим корневым сертификатом (CA).
3. Отдельно открывает настоящее TLS-соединение к настоящему example.com.
4. Теперь у прокси два расшифрованных потока, и он видит запросы и ответы
   как обычный текст.

Браузер согласится на подмену только если корневой сертификат прокси добавлен
в доверенные. На Windows 10 это хранилище «Доверенные корневые центры
сертификации»:

    certutil -addstore Root ca.crt

Firefox использует своё хранилище, туда добавлять отдельно.
Это единственный по-настоящему Windows-специфичный шаг во всём проекте.

Нюансы:

- Имя хоста для сертификата берётся из строки CONNECT или из SNI, поля
  в начале TLS-рукопожатия, где браузер сообщает целевой хост.
- Сертификаты нужно кэшировать, чтобы не генерировать заново на каждое соединение.

## Что происходит внутри программы дальше

После расшифровки поток проходит через конвейер:

- **Парсер HTTP.** Разбирает байты на метод, путь, заголовки, тело.
  Критично хранить сырые байты, а не только разобранную структуру,
  потому что нормализация прячет атаки.
- **Перехват (Intercept).** Если включён, запрос ставится на паузу,
  показывается пользователю, тот правит его и нажимает «отправить» или
  «сбросить». Технически это канал между сетевым потоком и UI:
  сетевая задача ждёт ответа от UI.
- **История.** Каждая пара запрос и ответ пишется в SQLite с метаданными:
  время, хост, статус, размер.
- **Replay.** Запрос из истории отправляется заново отдельным HTTP-клиентом,
  минуя прокси.
- **UI.** Отдельный процесс или окно, общается с ядром через API
  (у Caido это GraphQL поверх HTTP и WebSocket). Разделение позволяет ядру
  работать без окна.

## Словарь для промптов на Rust

- **tokio** — асинхронный runtime, на нём всё сетевое.
- **hyper** — HTTP-библиотека низкого уровня, режимы сервера и клиента.
- **rustls** — TLS-реализация; **tokio-rustls** её асинхронная обёртка.
- **rcgen** — генерация сертификатов и CA.
- **httparse** — низкоуровневый парсер HTTP без нормализации.
- **rusqlite** / **sqlx** — работа с SQLite.
- **hudsucker** — готовый MITM-прокси на этих компонентах; основа или учебный пример.
- **Tauri** — десктопное окно с веб-интерфейсом.

### Пример чёткого промпта на первый шаг

> Сделай на Rust с tokio и hyper HTTP-прокси, слушающий 127.0.0.1:8080.
> Для обычных запросов проксируй их на целевой хост и логируй метод, URL
> и статус. Для CONNECT делай MITM: генерируй сертификат на хост через rcgen,
> подписывай нашим CA из файла ca.pem, устанавливай TLS с клиентом через
> tokio-rustls, к серверу подключайся тоже через rustls. Сырые байты запроса
> и ответа сохраняй без изменений.

## План первых шагов

1. Создать проект (cargo).
2. Сгенерировать CA.
3. Установить CA в Windows.
4. Поднять прокси, который пока только логирует хосты.
5. Посмотреть трафик браузера через него.
