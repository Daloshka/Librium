# TCP handshake: как устанавливается соединение

[← Назад к индексу](../../README.ru.md) · Связано: [Сеть](../network.md), [Архитектура](../architecture.md)

---

## 1. Зачем нужен handshake

UDP отправляет датаграмму и забывает. TCP обещает надёжный поток байтов
в правильном порядке, а для этого обеим сторонам нужно заранее:

- убедиться, что вторая сторона существует и слушает нужный порт;
- договориться о начальных номерах байтов, чтобы потом отслеживать
  доставку и порядок;
- обменяться параметрами: максимальный размер сегмента, масштаб окна,
  поддержка выборочных подтверждений.

Handshake решает все три задачи за три сегмента.

---

## 2. Заголовок TCP-сегмента

Чтобы понимать handshake, нужно знать, какие поля есть в каждом сегменте.
Заголовок минимум 20 байт:

    ┌────────────────────────────┬────────────────────────────┐
    │  Порт источника (16 бит)   │  Порт назначения (16 бит)  │
    ├────────────────────────────┴────────────────────────────┤
    │             Sequence number, SEQ (32 бита)              │
    ├─────────────────────────────────────────────────────────┤
    │          Acknowledgment number, ACK (32 бита)           │
    ├──────┬─────────┬──────────┬─────────────────────────────┤
    │ Длина│ резерв  │  Флаги   │     Window (16 бит)         │
    │ загол│         │ SYN ACK  │                             │
    │ (4)  │         │ FIN RST  │                             │
    │      │         │ PSH URG  │                             │
    ├──────┴─────────┴──────────┼─────────────────────────────┤
    │   Контрольная сумма (16)  │     Urgent pointer (16)     │
    ├───────────────────────────┴─────────────────────────────┤
    │   Опции (до 40 байт): MSS, Window Scale, SACK, TS ...   │
    ├─────────────────────────────────────────────────────────┤
    │                     Данные (могут отсутствовать)         │
    └─────────────────────────────────────────────────────────┘

Что важно для handshake:

| Поле       | Смысл                                                              |
|------------|--------------------------------------------------------------------|
| SEQ        | Номер первого байта данных в этом сегменте, в нумерации отправителя |
| ACK        | «Я получил все байты до этого номера, жду следующий с этим номером» |
| Флаг SYN   | Синхронизация: «это начало, мой SEQ начинается отсюда»              |
| Флаг ACK   | Поле ACK в заголовке имеет смысл                                    |
| Флаг FIN   | «Я закончил отправку»                                              |
| Флаг RST   | Сброс: «такого соединения нет» или аварийный обрыв                  |
| Window     | Сколько байт готов принять без подтверждения                       |

## 3. Три сегмента

Обозначим: клиент выбрал начальный номер `x`, сервер выбрал `y`.
Начальные номера (ISN, Initial Sequence Number) случайные, чтобы старые
сегменты из прошлых соединений и подделанные пакеты не совпали
с текущим соединением.

    Клиент                                          Сервер
    (CLOSED)                                        (LISTEN на порту 8080)
       │                                               │
       │  ① SYN                                        │
       │    SEQ = x                                    │
       │    флаги: SYN                                 │
       │    опции: MSS=1460, WS=8, SACK-OK, TS         │
       │──────────────────────────────────────────────▶│
    (SYN-SENT)                                         │  сервер запоминает x,
       │                                               │  выбирает y
       │                                               │
       │  ② SYN + ACK                                  │
       │    SEQ = y                                    │
       │    ACK = x + 1                                │
       │    флаги: SYN, ACK                            │
       │    опции: MSS=1460, WS=7, SACK-OK, TS         │
       │◀──────────────────────────────────────────────│
       │                                          (SYN-RECEIVED)
       │  клиент проверяет ACK == x+1,                 │
       │  запоминает y                                 │
       │                                               │
       │  ③ ACK                                        │
       │    SEQ = x + 1                                │
       │    ACK = y + 1                                │
       │    флаги: ACK                                 │
       │──────────────────────────────────────────────▶│
    (ESTABLISHED)                                 (ESTABLISHED)
       │                                               │
       │  данные: SEQ = x+1, первый байт полезной      │
       │  нагрузки, например «CONNECT example.com...»  │
       │──────────────────────────────────────────────▶│

Почему ACK равен `x + 1`, хотя данных не было: флаг SYN сам занимает один
номер в последовательности, как если бы это был один байт. То же с FIN.
Это позволяет подтверждать сам факт получения SYN.

Что каждая сторона узнала:

- После ② клиент знает, что сервер жив, слушает порт и получил его SYN.
- После ③ сервер знает, что клиент получил его SYN-ACK, и что клиент
  настоящий, а не подделанный адрес: ответить правильным `y+1` может
  только тот, кто получил ②. Это защита от подмены адреса источника.

Стоимость: один полный круг (RTT) до отправки первого байта данных.
Данные можно приложить уже к сегменту ③, и обычно так и происходит:
браузер отправляет ACK и сразу ClientHello или CONNECT.

## 4. Опции, о которых договариваются

Опции передаются только в SYN и SYN-ACK, потом они зафиксированы.

- **MSS (Maximum Segment Size).** Максимум байт данных в одном сегменте.
  Обычно 1460 для Ethernet: MTU 1500 минус 20 байт IP минус 20 байт TCP.
  Каждая сторона объявляет свой, используется меньший.
- **Window Scale.** Поле Window в заголовке 16-битное, максимум 65535 байт.
  Для быстрых сетей мало. Опция задаёт множитель: WS=8 означает,
  что реальное окно это Window × 256.
- **SACK Permitted.** Разрешает выборочные подтверждения: «получил байты
  1000..2000 и 3000..4000, дыра 2000..3000». Без SACK при потере одного
  сегмента пришлось бы повторять всё после него.
- **Timestamps.** Метки времени в каждом сегменте для точного измерения
  RTT и защиты от старых сегментов при переполнении номеров.

Если одна сторона опцию не предложила, она не используется.

## 5. Что происходит внутри ОС

**Сторона сервера.** Когда Librium вызывает `TcpListener::bind` и начинает
`accept`, стек tcpip.sys создаёт слушающий сокет в состоянии LISTEN
и две очереди:

    SYN получен ──▶ [очередь полуоткрытых, SYN queue]
                          │ пришёл ACK ③
                          ▼
                    [очередь готовых, accept queue] ──▶ accept() отдаёт сокет

Весь handshake делает ядро. Программа получает из `accept` уже
установленное соединение, а первые байты данных возможно уже лежат
в его буфере. Размер очереди готовых задаётся параметром backlog.
Если программа не успевает вызывать `accept` и очередь переполнена,
новые SYN отбрасываются или получают RST.

**Сторона клиента.** Вызов `TcpStream::connect` отправляет SYN и блокирует
(в async варианте: задача засыпает) до прихода SYN-ACK. Порт источника
ядро выбирает автоматически из эфемерного диапазона, на Windows 10
это 49152..65535.

## 6. Что бывает, когда что-то не так

| Ситуация                                   | Что видит клиент                              |
|--------------------------------------------|-----------------------------------------------|
| На порту никто не слушает                  | В ответ на SYN приходит **RST**, ошибка сразу: «Connection refused» |
| Хост есть, но брандмауэр молча роняет SYN  | Ответа нет, клиент повторяет SYN с растущими интервалами, через ~20 с «Connection timed out» |
| Хост недоступен на уровне IP               | ICMP «unreachable» от маршрутизатора, ошибка «No route to host» |
| Очередь на сервере переполнена             | Как молчание брандмауэра, SYN теряется        |
| SYN-ACK пришёл с неправильным ACK          | Клиент отвечает RST, соединение не создаётся  |

Повторы SYN: первый через 1 с, потом 2, 4, 8 с. Отсюда долгие зависания
при недоступном хосте.

---

## 7. SYN flood и SYN cookies

Атакующий шлёт много SYN с поддельных адресов и не отвечает на SYN-ACK.
Очередь полуоткрытых забивается, настоящие клиенты не могут подключиться.
Защита SYN cookies: сервер не хранит запись о полуоткрытом соединении,
а кодирует нужные данные прямо в своём ISN `y`. Когда приходит ③ с `y+1`,
сервер восстанавливает состояние из номера. Windows включает похожую
защиту автоматически при перегрузке.

Для Librium это не угроза, порт слушает только localhost, но это объясняет,
почему ISN должен быть непредсказуемым.

## 8. Закрытие соединения

Не часть handshake, но симметричная картина. Каждая сторона закрывает
свою половину отдельно, четыре сегмента:

    Клиент                              Сервер
       │  FIN, SEQ=m                       │
       │──────────────────────────────────▶│   клиент больше не пишет,
       │  ACK=m+1                          │   но может читать
       │◀──────────────────────────────────│
       │       ... сервер дописывает ...   │
       │  FIN, SEQ=n                       │
       │◀──────────────────────────────────│
       │  ACK=n+1                          │
       │──────────────────────────────────▶│
    (TIME-WAIT, 2×MSL,                 (CLOSED)
     на Windows 30 с)

Сторона, закрывшая первой, задерживается в TIME-WAIT, чтобы запоздавшие
сегменты старого соединения не попали в новое с той же четвёркой.
Отсюда тысячи соединений в TIME-WAIT в `netstat` после нагрузки.

RST вместо FIN означает аварийный обрыв: данные в буферах теряются.
Прокси получает RST, например, когда сервер сбросил соединение,
и должен корректно передать обрыв браузеру.

---

## 9. Что из этого видит Librium

Ничего из handshake напрямую. Всё делает tcpip.sys, а прокси получает
готовый `TcpStream` из `accept` и готовый `TcpStream` из `connect`.
Но понимать это нужно, чтобы:

- правильно читать ошибки: «refused» значит порт закрыт, «timed out»
  значит пакеты роняются;
- ставить таймаут на `connect` к серверу, иначе задача повиснет
  на 20 секунд на каждом недоступном хосте;
- не удивляться TIME-WAIT в netstat и понимать, почему повторный
  `bind` на 8080 сразу после остановки может не сработать
  (на Windows это редко, на Linux нужен SO_REUSEADDR);
- в v3 с WinDivert, где handshake придётся обрабатывать самому,
  знать, что именно происходит.

## 10. Увидеть в Wireshark

Фильтр `tcp.flags.syn == 1` покажет только ① и ②. Фильтр
`tcp.port == 8080` и первые три строки любого соединения это handshake:

    1  51234 → 8080  [SYN]      Seq=0            MSS=1460 WS=256 SACK_PERM
    2  8080  → 51234 [SYN, ACK] Seq=0 Ack=1      MSS=1460 WS=256 SACK_PERM
    3  51234 → 8080  [ACK]      Seq=1 Ack=1
    4  51234 → 8080  [PSH, ACK] Seq=1 Ack=1 Len=42   ← CONNECT example.com:443

Wireshark показывает относительные номера, начиная с 0, а не настоящие
случайные ISN. Отключается в настройках протокола TCP.
