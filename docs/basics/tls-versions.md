# Версии TLS: чем отличаются и что используется сегодня

[← Назад к индексу](../../README.md) · Связано: [Криптография TLS](tls-crypto.md), [Сертификаты](certificates.md), [Глоссарий](protocols.md#tls-transport-layer-security)

---

## 1. Хронология

| Версия  | Год  | Статус сегодня                                     |
|---------|------|----------------------------------------------------|
| SSL 1.0 | —    | Никогда не выпускался, дыры нашли до релиза         |
| SSL 2.0 | 1995 | Сломан, запрещён (RFC 6176)                         |
| SSL 3.0 | 1996 | Сломан атакой POODLE, запрещён (RFC 7568)           |
| TLS 1.0 | 1999 | Устарел, отключён в браузерах с 2020, запрещён PCI DSS |
| TLS 1.1 | 2006 | Устарел, отключён вместе с 1.0                      |
| **TLS 1.2** | 2008 | Основной рабочий, поддерживается везде          |
| **TLS 1.3** | 2018 | Основной современный, по умолчанию у всех новых клиентов |

Имя сменилось с SSL на TLS при передаче стандарта в IETF в 1999 году.
Технически SSL мёртв больше десяти лет, но слово осталось: «SSL-сертификат»,
«SSL-соединение» означают TLS.

Проверено в примере, OpenSSL 3.5.4:

    tls1     -> no protocols available   (клиент отказывается даже предлагать)
    tls1_1   -> no protocols available
    tls1_2   -> Protocol: TLSv1.2        ok
    tls1_3   -> Protocol: TLSv1.3        ok

То есть современный OpenSSL собран вообще без старых версий, их нельзя
включить флагом. Это типичная ситуация для всех новых библиотек, включая
rustls, которая поддерживает только 1.2 и 1.3.

## 2. Главное отличие 1.3 от 1.2: скорость

### TLS 1.2, два круга до данных

    Клиент                                      Сервер
       │── ClientHello ────────────────────────▶│   ⎫
       │◀── ServerHello, Certificate,           │   ⎬ круг 1
       │    ServerKeyExchange, ServerHelloDone ─│   ⎭
       │── ClientKeyExchange, ChangeCipherSpec, │   ⎫
       │   Finished ───────────────────────────▶│   ⎬ круг 2
       │◀── ChangeCipherSpec, Finished ─────────│   ⎭
       │══ данные ═════════════════════════════▶│

Плюс круг на TCP handshake, итого три круга до первого байта HTTP.
На канале с задержкой 50 мс это 150 мс впустую.

### TLS 1.3, один круг

    Клиент                                      Сервер
       │── ClientHello + key_share ────────────▶│   ⎫
       │◀── ServerHello + key_share,            │   ⎬ круг 1
       │    {EncryptedExtensions, Certificate,  │   │
       │     CertificateVerify, Finished} ──────│   ⎭
       │── {Finished} ═════════════════════════▶│
       │══ данные ═════════════════════════════▶│

Фигурные скобки означают «уже зашифровано». Трюк в том, что клиент
угадывает алгоритм обмена ключами и присылает свою половину ключа сразу
в ClientHello. Сервер отвечает своей половиной, и общий секрет готов уже
после первого ответа. Всё остальное, включая сертификат, летит
зашифрованным.

### 0-RTT, повторное подключение

Если клиент уже общался с сервером, он может отправить данные вместе
с самым первым сообщением, ноль кругов ожидания. Плата за это: такие
данные уязвимы к повторной отправке злоумышленником, поэтому 0-RTT
разрешён только для безопасных операций вроде GET.

## 3. Чем ещё отличается 1.3

**Выкинули всё сломанное.** В 1.2 было около 350 наборов шифров, среди них
RC4, 3DES, MD5, экспортные шифры, режим CBC с его атаками (BEAST, Lucky13),
статический RSA без прямой секретности. В 1.3 осталось пять наборов,
все с аутентифицированным шифрованием AEAD:

    TLS_AES_128_GCM_SHA256
    TLS_AES_256_GCM_SHA384
    TLS_CHACHA20_POLY1305_SHA256
    TLS_AES_128_CCM_SHA256
    TLS_AES_128_CCM_8_SHA256

Заметьте формат имени: в 1.2 имя включало способ обмена ключами
и аутентификации (`ECDHE-RSA-AES128-GCM-SHA256`), в 1.3 только шифр
и хеш, потому что обмен ключами всегда эфемерный.

**Прямая секретность обязательна.** В 1.3 обмен ключами всегда эфемерный
(ECDHE или DHE): ключи сессии существуют только на время соединения.
Даже если завтра украдут приватный ключ сервера, вчерашний записанный
трафик расшифровать не выйдет. В 1.2 это было опционально, и многие
использовали статический RSA, где кража ключа вскрывает весь архив.

**Больше зашифровано.** В 1.2 сертификат сервера летел открытым текстом,
и любой наблюдатель видел, на какой домен выдан. В 1.3 сертификат
зашифрован. Снаружи остаётся видно только SNI, имя хоста в ClientHello,
и его прячет отдельное расширение ECH.

**Подпись всего рукопожатия.** Сообщение CertificateVerify подписывает
всю предыдущую переписку, что закрывает целый класс атак с понижением
версии и подменой параметров.

## 4. Почему TLS 1.2 всё ещё жив

Не из-за упрямства, а по трём причинам:

- **Старые клиенты.** Windows 7, Android до 10, Java 8 без обновлений,
  встроенные устройства. Отключив 1.2, сайт теряет часть аудитории.
- **Промежуточное оборудование.** Корпоративные файрволы, DPI,
  балансировщики, которые умеют разбирать 1.2 и ломаются на 1.3.
- **Инспекция трафика.** Именно то, что делает Librium, только
  в корпоративном масштабе. С 1.3 это сложнее, часть решений застряла.

Правильная сегодняшняя настройка сервера: включены 1.2 и 1.3, всё
остальное отключено. Именно так настроены github.com и example.com,
проверено выше.

## 5. Что это значит для Librium

**Какие версии поддерживать.** rustls умеет только 1.2 и 1.3, и этого
достаточно. Специально добавлять 1.0 и 1.1 не нужно, а если попадётся
древний сервер, соединение просто не установится, и это надо показать
пользователю понятной ошибкой, а не паникой.

**Прокси согласовывает версию дважды и независимо.** С браузером
он сервер, с сайтом он клиент. Версии могут не совпадать: браузер
договорился на 1.3, а сайт умеет только 1.2. Это нормально и никого
не смущает, потому что между ними расшифрованный HTTP.

**Инструмент безопасности должен уметь говорить плохо.** Отдельная
функция на будущее: разрешить пользователю подключаться к серверу
с ослабленными настройками, чтобы проверить, принимает ли тот
устаревшие шифры. Для этого rustls не подойдёт, он принципиально
не даёт себя ослабить, понадобится openssl или native-tls.

**Показывать версию в интерфейсе.** Для каждого запроса полезно
видеть согласованную версию TLS, набор шифров и группу обмена ключами
с обеих сторон. Это готовая находка для отчёта, если сервер
поддерживает что-то устаревшее.

## 6. Проверить самому

Какие версии принимает конкретный сервер:

    openssl s_client -connect example.com:443 -servername example.com -tls1_2
    openssl s_client -connect example.com:443 -servername example.com -tls1_3

Смотреть строку `Protocol :` в блоке SSL-Session. Если версия
не поддерживается, будет `handshake failure` или `no protocols available`,
второе означает, что отказался сам клиент.

Полный список того, что умеет сервер, показывает `nmap`:

    nmap --script ssl-enum-ciphers -p 443 example.com

Онлайн-вариант с оценкой: SSL Labs, `ssllabs.com/ssltest`.
