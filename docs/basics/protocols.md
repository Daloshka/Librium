## Канальный уровень: доставка в пределах одной сети

### Ethernet

Стандарт проводной локальной сети: как кодировать биты в провод, как
делить среду между устройствами, как выглядит кадр. Работает только
внутри одной локальной сети: коммутатор пересылает кадр по MAC-адресу,
за пределы сети кадр не выходит, там маршрутизатор снимает старый
заголовок Ethernet и надевает новый, для следующей сети.

#### Из чего состоит кадр

Современный формат называется Ethernet II. Слева направо, как байты
идут в провод:

    │◀────── добавляет сетевая карта ──────▶│◀─────── видит ОС ───────▶│◀ карта ▶│

    ┌──────────┬─────┬─────────┬─────────┬──────┬───────────────────┬───────┐
    │ Преамбула│ SFD │ MAC dst │ MAC src │ Type │     Данные        │  FCS  │
    │  7 байт  │  1  │ 6 байт  │ 6 байт  │  2   │   46..1500 байт   │   4   │
    └──────────┴─────┴─────────┴─────────┴──────┴───────────────────┴───────┘
                     │◀────── заголовок 14 байт ─────▶│
                     │◀──────── кадр, 64..1518 байт ────────────────────────▶│

    Преамбула  10101010 × 7 — синхронизация приёмника, «сейчас будет кадр»
    SFD        10101011      — Start Frame Delimiter, «кадр начинается сейчас»
    MAC dst    кому, 48 бит
    MAC src    от кого, 48 бит
    Type       что внутри: 0x0800 IPv4, 0x86DD IPv6, 0x0806 ARP, 0x8100 VLAN
    Данные     полезная нагрузка, обычно целиком IP-пакет
    FCS        Frame Check Sequence, CRC32 по кадру; не сошлось — кадр молча выброшен

После кадра идёт межкадровый интервал (interframe gap) 12 байт тишины.

#### Что в поле «Данные»

Ровно то, что передал верхний уровень, чаще всего целиком IP-пакет,
а внутри него TCP-сегмент, а внутри уже TLS и HTTP:

    ┌─ Ethernet, 14 байт заголовка ──────────────────────────────────────┐
    │ dst │ src │ 0x0800 │                                          │FCS │
    │     │     │        │ ┌─ IPv4, 20 байт ────────────────────────┐    │
    │     │     │        │ │ версия, TTL, протокол=6, IP src, IP dst│    │
    │     │     │        │ │ ┌─ TCP, 20 байт ─────────────────────┐ │    │
    │     │     │        │ │ │ порты, SEQ, ACK, флаги, окно       │ │    │
    │     │     │        │ │ │ ┌─ данные приложения ────────────┐ │ │    │
    │     │     │        │ │ │ │ TLS-запись, внутри HTTP        │ │ │    │
    │     │     │        │ │ │ └────────────────────────────────┘ │ │    │
    │     │     │        │ │ └────────────────────────────────────┘ │    │
    │     │     │        │ └────────────────────────────────────────┘    │
    └────────────────────────────────────────────────────────────────────┘

Арифметика MTU: 1500 байт данных минус 20 байт IPv4 минус 20 байт TCP
даёт 1460 байт полезной нагрузки. Это и есть типичный MSS из
[TCP handshake](tcp-handshake.md#4-опции-о-которых-договариваются).
С IPv6 заголовок 40 байт, остаётся 1440.

Границы размера. Минимум данных 46 байт: короткий кадр добивается
нулями, иначе на старом коллизионном Ethernet отправитель не успел бы
заметить столкновение. Максимум 1500 байт, это MTU. Бывают jumbo-кадры
до 9000 байт, но только если их поддерживает всё оборудование по пути.

#### Как устроен MAC-адрес

48 бит, записывается шестью байтами через двоеточие или дефис:

    3C : 52 : 82 : 1A : 9F : 00
    └──── OUI ────┘ └── серийный ──┘
     кто произвёл    номер карты у производителя

- **OUI** (Organizationally Unique Identifier) первые три байта,
  закреплены за производителем. По ним определяется вендор карты.
- Два служебных бита в первом байте: младший бит первого байта равен 1
  у групповых адресов, второй младший равен 1 у локально назначенных
  (например когда телефон подменяет MAC для приватности в Wi-Fi).
- `FF:FF:FF:FF:FF:FF` это широковещательный адрес, кадр примут все
  в сегменте. Так работает ARP, поиск MAC по известному IP.

Посмотреть свои: `getmac /v` или `ipconfig /all` в строке
«Физический адрес».

#### Что из этого касается Librium

Напрямую ничего: прокси работает на уровне приложения и получает
собранный поток байтов. Косвенно два факта:

- MTU 1500 задаёт MSS 1460, поэтому большой HTTP-ответ приходит
  сотнями сегментов, и склеивает их TCP-стек, а не Librium;
- в Wireshark каждая строка это именно кадр Ethernet, и его заголовок
  видно первым при разборе пакета.

### Wi-Fi (IEEE 802.11)

То же, что Ethernet, но по радио. Те же MAC-адреса, те же кадры сверху,
плюс свои механизмы: точка доступа, шифрование канала (WPA2, WPA3),
борьба за эфир. Для всех уровней выше Wi-Fi неотличим от Ethernet.

Для Librium: единственная точка, где Wi-Fi важен, это перехват трафика
телефона. Телефон и компьютер должны быть в одной Wi-Fi-сети, чтобы
телефон мог достучаться до `<IP компьютера>:8080`.

## Сетевой уровень: доставка между сетями

### IP (Internet Protocol)

Протокол, который переносит пакет от одного хоста к другому через любое
число промежуточных сетей. Каждый пакет несёт IP-адрес отправителя
и получателя, маршрутизаторы по адресу получателя решают, куда передать
дальше. IP ничего не гарантирует: пакет может потеряться, прийти
дважды, прийти не по порядку. Надёжность строится выше, в TCP.

### IPv4

Четвёртая версия IP, основная с 1981 года. Адрес 32 бита, записывается
четырьмя числами: `192.0.2.10`. Всего около 4 миллиардов адресов,
их давно не хватает, отсюда NAT: домашний роутер выдаёт устройствам
частные адреса (`192.168.x.x`, `10.x.x.x`), а наружу все ходят
с одного публичного.

Для Librium: `127.0.0.1` это loopback, адрес самой машины. Прокси
слушает его, чтобы быть недоступным извне. `0.0.0.0` означает
«все интерфейсы», нужно для телефона в той же сети.

### IPv6

Шестая версия, замена IPv4. Адрес 128 бит, записывается шестнадцатеричными
группами: `2606:2800:220:1:248:1893:25c8:1946`, нули сокращаются
через `::`. Адресов практически бесконечно, NAT не нужен. Loopback
записывается как `::1`. Сосуществует с IPv4: у большинства сайтов есть
оба адреса, DNS возвращает оба (A и AAAA), клиент пробует IPv6
первым (Happy Eyeballs).

Для Librium: при подключении к серверу резолвер может вернуть IPv6-адрес,
и прокси должен уметь к нему подключиться либо откатиться на IPv4.
Слушать стоит и `127.0.0.1`, и `::1`, потому что `localhost` в Windows
может резолвиться в любой из них.

### ICMP (Internet Control Message Protocol)

Служебный протокол IP-уровня, портов нет. Маршрутизаторы и хосты
сообщают им о проблемах: «сеть недоступна», «порт недоступен»,
«время жизни пакета истекло», «пакет слишком большой». Отдельные
сообщения Echo Request и Echo Reply используются утилитой ping для
проверки доступности, traceroute строит маршрут на сообщениях
об истёкшем времени жизни.

Для Librium: невидим, но объясняет ошибки. «No route to host» это
пришедшее ICMP. Подробнее в [network.md, раздел 6](../network.md#6-icmp-и-ping).

## Транспортный уровень: доставка между программами

### TCP (Transmission Control Protocol)

Надёжный поток байтов между двумя программами. Поверх ненадёжного IP
добавляет: установление соединения ([handshake](tcp-handshake.md)),
нумерацию байтов, подтверждения, повторную отправку потерянного,
восстановление порядка, управление скоростью. Программы адресуются
портами (16 бит, 0..65535): HTTP 80, HTTPS 443, SMTP 25 и так далее.
Соединение однозначно определяется четвёркой IP и портов обеих сторон.

Для Librium: основа всего. Прокси это TCP-сервер на 8080 и TCP-клиент
к целевым серверам. Прокси видит поток байтов, а не пакеты.

### UDP (User Datagram Protocol)

Отправка отдельных датаграмм без соединения и без гарантий. Заголовок
8 байт: два порта, длина, контрольная сумма. Нет handshake, нет повторов,
нет порядка. Взамен минимальная задержка и отсутствие накладных расходов,
поэтому UDP выбирают там, где потерянный пакет лучше пропустить, чем
ждать повтора: голос, видео, игры, DNS, QUIC.

Для Librium v1: не перехватывается, HTTP-прокси не умеет UDP.
Подробнее в [network.md, раздел 5](../network.md#5-udp).

### QUIC

Транспортный протокол от Google, стандартизован в 2021 году, работает
поверх UDP. Переизобретает TCP с учётом опыта: несколько независимых
потоков в одном соединении (потеря пакета в одном не тормозит другие),
TLS 1.3 встроен внутрь, handshake транспорта и шифрования совмещены
в один круг (или ноль при повторном подключении), соединение переживает
смену IP-адреса, например при переходе с Wi-Fi на мобильную сеть.
Почти всё, включая большую часть служебных заголовков, зашифровано.
Основное применение HTTP/3.

Для Librium: браузеры не используют QUIC через HTTP-прокси, откатываются
на TCP. Поэтому v1 его не касается. Перехват QUIC требует прозрачного
режима и собственного QUIC-стека, это v3.

## Прикладной уровень: смысл данных

### DNS (Domain Name System)

Распределённая база, переводящая имена в адреса: `example.com` в
`192.0.2.10`. Клиент спрашивает резолвер (обычно провайдера, роутера
или публичный вроде 1.1.1.1), тот при необходимости обходит корневые
серверы, серверы зоны `.com`, серверы самого домена. Типы записей:
A (IPv4), AAAA (IPv6), CNAME (псевдоним), MX (почтовый сервер),
TXT (произвольный текст). Классически работает по UDP 53 открытым
текстом, современные варианты DoH (поверх HTTPS) и DoT (поверх TLS)
шифруют запросы.

Для Librium: с настроенным прокси браузер DNS не делает вообще, он
передаёт имя хоста в CONNECT, и резолвит уже прокси. Это удобно:
прокси может подменять адреса, направляя `example.com` на тестовый сервер.

### TLS (Transport Layer Security)

Слой шифрования и проверки подлинности поверх TCP. Раньше назывался
SSL, старое имя до сих пор в ходу. Даёт три вещи: конфиденциальность
(никто по пути не читает), целостность (никто не изменит незаметно),
подлинность сервера (сертификат, подписанный доверенным центром,
доказывает, что это действительно example.com). Начинается
с handshake, где стороны договариваются об алгоритмах и вырабатывают
общий ключ, дальше данные идут зашифрованными записями. Актуальная
версия 1.3, версия 1.2 ещё широко используется, старше считаются
небезопасными.

HTTPS это HTTP внутри TLS. SMTPS, IMAPS, FTPS по той же схеме.

Подробно про версии: [Версии TLS](tls-versions.md). Про устройство
сертификатов и что значит CN: [Сертификаты](certificates.md).

Для Librium: центральная тема. Прокси ломает третье свойство, подлинность,
подставляя свой сертификат, и это работает только потому, что
пользователь сам добавил CA прокси в доверенные. Подробно в
[network.md, раздел 4](../network.md#4-https-полная-хронология-одного-запроса).

### HTTP (HyperText Transfer Protocol)

Протокол запрос-ответ для веба. Клиент отправляет запрос: метод
(GET, POST, PUT, DELETE), путь, версия, заголовки, тело. Сервер отвечает:
код статуса (200, 404, 500), заголовки, тело. Без состояния: каждый
запрос независим, сессии эмулируются куками.

Версии:

- **HTTP/1.1** (1997): текстовый, по одному запросу за раз в соединении,
  соединение переиспользуется (keep-alive). Самый простой для чтения
  и отладки.
- **HTTP/2** (2015): бинарный, те же семантика и заголовки, но несколько
  запросов одновременно в одном соединении (мультиплексирование), сжатие
  заголовков. Почти всегда внутри TLS, протокол выбирается через ALPN.
- **HTTP/3** (2022): HTTP/2 поверх QUIC вместо TCP.

Для Librium: главный объект работы. v1 говорит HTTP/1.1 с обеих сторон,
HTTP/2 добавляется во v2.

### WebSocket

Двусторонний канал поверх одного TCP-соединения, начинающийся как
HTTP-запрос. Клиент шлёт обычный GET с заголовком `Upgrade: websocket`,
сервер отвечает статусом 101 Switching Protocols, и с этого момента
в соединении идут не HTTP-сообщения, а кадры WebSocket в обе стороны
в любой момент, без схемы запрос-ответ. Используется для чатов, живых
обновлений, игр в браузере. `ws://` открытый, `wss://` внутри TLS.

Для Librium: прокси видит Upgrade-запрос как обычный HTTP, а после 101
должен переключиться в режим пересылки кадров и показывать их отдельно
от HTTP-истории. Caido и Burp это умеют, для v1 достаточно слепо
пересылать байты после 101.

### SMTP (Simple Mail Transfer Protocol)

Отправка почты между клиентом и сервером и между серверами. Текстовый
диалог: клиент здоровается (EHLO), называет отправителя (MAIL FROM),
получателей (RCPT TO), передаёт письмо (DATA). Порты: 25 между
серверами, 587 для клиентов с STARTTLS, 465 с TLS сразу. Только
отправка: чтение почты это IMAP или POP3.

Для Librium: за пределами HTTP-прокси, но иллюстрирует STARTTLS,
когда TLS начинается не с первого байта, а по команде. Подробнее в
[network.md, раздел 7](../network.md#7-smtp-и-другие-протоколы-поверх-tcp).

## Кто на ком стоит

    HTTP/1.1 ──┐
    HTTP/2   ──┼── TLS ── TCP ── IP ── Ethernet / Wi-Fi
    WebSocket ─┘        (или без TLS напрямую на TCP)
    SMTP ──────── TLS или STARTTLS ── TCP ── IP ── ...
    HTTP/3 ───── QUIC (TLS внутри) ── UDP ── IP ── ...
    DNS ──────── UDP ── IP ── ...   (или DoH: HTTPS, DoT: TLS ── TCP)
    ping ─────── ICMP ── IP ── ...

Зона Librium v1: верхняя строка, всё что внутри TLS поверх TCP.
