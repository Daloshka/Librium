# Сертификаты: что значит CN и остальные буквы

[← Назад к индексу](../../README.md) · Связано: [Центры сертификации](certificate-authorities.md), [Версии TLS](tls-versions.md), [Криптография TLS](tls-crypto.md), [Настройка прокси](../proxy-setup.md#6-установка-корневого-сертификата-librium)

---

## 1. Откуда берутся эти буквы

Сертификат это структура стандарта X.509. Участники в нём описываются
не одной строкой, а набором пар «атрибут = значение». Такой набор
называется **DN** (Distinguished Name), различительное имя. Буквы вроде
`CN` и `O` это сокращённые имена атрибутов из стандарта X.500, откуда
X.509 родом.

Записывается через запятую:

    C=US, ST=California, L=Los Angeles, O=Internet Corporation for Assigned Names and Numbers, CN=example.com

В выводе openssl вы видите две строки на каждое звено цепочки:

    0 s:CN=example.com
      i:C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication CA DV E36

- **s:** это subject, кому выдан сертификат;
- **i:** это issuer, кто его выдал, то есть subject следующего звена вверх.

## 2. Расшифровка атрибутов

| Код   | Полное имя           | Что означает                                  | Пример                        |
|-------|----------------------|-----------------------------------------------|-------------------------------|
| **CN**| Common Name          | Основное имя. Для сервера это домен, для CA его название, для человека имя | `example.com`, `Librium CA` |
| **O** | Organization         | Организация                                   | `Sectigo Limited`             |
| **OU**| Organizational Unit  | Подразделение внутри организации              | `IT Department`               |
| **C** | Country              | Страна, две буквы по ISO 3166                 | `US`, `GB`, `RU`              |
| **ST**| State or Province    | Область или штат. Не «street», частая путаница| `California`                  |
| **L** | Locality             | Город или населённый пункт                    | `Los Angeles`                 |
| **STREET** | Street Address  | Улица                                         | `1 Main St`                   |
| **postalCode** | Почтовый индекс | Индекс                                    | `90292`                       |
| **emailAddress** | Email      | Почта, устаревшее для серверных сертификатов  | `admin@example.com`           |
| **SN** | serialNumber        | Регистрационный номер организации. Осторожно: в некоторых инструментах `SN` это surname, фамилия | `12345678` |
| **GN** | givenName           | Имя человека                                  | `Ivan`                        |
| **DC** | Domain Component    | Часть домена, используется в LDAP и Active Directory | `DC=example, DC=com`   |
| **UID**| userId              | Идентификатор пользователя                    | `ivanov`                      |

Из них для веб-сертификатов реально важен только **CN**, остальные либо
не заполняются, либо носят справочный характер.

---

## 3. CN больше не главный

Исторически браузер сравнивал запрошенный домен с полем CN. С 2017 года
все браузеры это прекратили. Теперь имена берутся **только** из расширения
**SAN** (Subject Alternative Name), а CN игнорируется при проверке.

Реальный сертификат github.com, снят в примере:

    subject = CN=github.com
    issuer  = C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication CA DV E36
    notBefore = Sep  1 00:00:00 2026 GMT
    notAfter  = Nov 29 23:59:59 2026 GMT
    X509v3 Subject Alternative Name:
        DNS:github.com, DNS:www.github.com
    X509v3 Key Usage: critical
        Digital Signature
    X509v3 Basic Constraints: critical
        CA:FALSE

CN здесь дублирует первое имя из SAN, это делается для совместимости
со старым софтом. Проверяет браузер именно строку SAN.

**Практический вывод для Librium.** Генерируя сертификат на лету, надо
обязательно заполнять SAN, а не только CN. Сертификат с одним CN
современный браузер отвергнет с ошибкой `ERR_CERT_COMMON_NAME_INVALID`.
В rcgen это `SanType::DnsName`. Если хост это IP-адрес, нужен
`SanType::IpAddress`, не DNS-имя.

В SAN можно писать маску: `DNS:*.example.com` покрывает поддомены
одного уровня, но не сам `example.com` и не `a.b.example.com`.

## 4. Остальные важные поля

**Validity, срок действия.** `notBefore` и `notAfter`. У github.com выше
срок около 90 дней, это современная норма: публичные центры больше
не выдают сертификаты дольше чем на 398 дней, и планка снижается.
Для CA Librium срок можно ставить большой, несколько лет, а для листовых
сертификатов достаточно нескольких дней.

**Basic Constraints.** Ключевое поле, отличающее центр от обычного
сертификата. `CA:FALSE` означает «этим сертификатом нельзя подписывать
другие». У корневого CA будет `CA:TRUE`, часто с ограничением глубины
цепочки `pathlen`. Пометка `critical` означает, что клиент обязан понять
это расширение, иначе должен отвергнуть сертификат.

**Key Usage и Extended Key Usage.** Для чего разрешено использовать ключ.
У сервера обычно `Digital Signature` и `Key Encipherment`, плюс
`serverAuth` в расширенном. У CA будет `Certificate Sign` и `CRL Sign`.
Если Librium выдаст лист без `serverAuth`, браузер откажет.

**Serial Number.** Уникальный номер, присвоенный выдавшим центром.
Должен быть непредсказуемым и не повторяться. Для Librium: генерировать
случайный, иначе браузер будет ругаться на два разных сертификата
с одинаковым номером от одного CA, а такое случается при перегенерации.

**Signature Algorithm.** Чем подписан, например `ecdsa-with-SHA256`
или `sha256WithRSAEncryption`. Подпись ставит **выдавший** центр
своим приватным ключом, поэтому проверить её можно публичным ключом
из сертификата уровнем выше.

**Public Key.** Публичный ключ самого субъекта, RSA 2048 бит или
ECDSA P-256. Именно им сервер доказывает владение через
CertificateVerify в [handshake](tls-versions.md#2-главное-отличие-13-от-12-скорость).

## 5. Как читается цепочка

    0 s:CN=github.com                    ← лист, ему верит браузер после проверки
      i:CN=Sectigo ... CA DV E36
                    ↑ подписал
    1 s:CN=Sectigo ... CA DV E36         ← промежуточный
      i:CN=Sectigo Public Server Auth Root
                    ↑ подписал
    2 s:CN=Sectigo Public Server Auth Root  ← корень, лежит в хранилище ОС

Проверка идёт снизу вверх: подпись листа проверяется ключом промежуточного,
подпись промежуточного ключом корня, а корню верят просто потому, что он
установлен в системе. Сервер обязан прислать все звенья кроме корня.

Зачем промежуточные вообще нужны: приватный ключ корня хранится офлайн
в сейфе и достаётся раз в несколько лет. Промежуточный работает
ежедневно, и если он скомпрометирован, отзывают только его, а не корень
из миллиардов устройств.

**Цепочка Librium будет короткой:**

    0 s:CN=example.com                   ← генерируется на лету
      i:CN=Librium CA
    1 s:CN=Librium CA                    ← самоподписанный, стоит в хранилище Windows

Два звена вместо четырёх, промежуточный не нужен.

## 6. Три уровня проверки при выдаче

Видно по названию центра и по заполненности полей:

- **DV** (Domain Validation). Центр проверил только контроль над доменом,
  обычно через файл на сайте или запись в DNS. Заполнен один CN.
  У github.com выше именно `CA DV`. Так работают Let's Encrypt и почти
  весь современный веб.
- **OV** (Organization Validation). Проверена ещё и организация,
  в subject появляются O, C, L.
- **EV** (Extended Validation). Углублённая проверка юрлица. Раньше
  давала зелёную строку с названием компании в адресной строке,
  браузеры от неё отказались, и разница осталась только в полях.

Для шифрования разницы нет никакой, отличается только объём проверки
владельца.

## 7. Команды для разбора

Посмотреть сертификат живого сайта:

    openssl s_client -connect github.com:443 -servername github.com -showcerts

Вытащить конкретные поля:

    openssl s_client -connect github.com:443 -servername github.com 2>$null |
      openssl x509 -noout -subject -issuer -dates -ext subjectAltName,keyUsage,basicConstraints

Разобрать файл целиком, человекочитаемо:

    openssl x509 -in ca.crt -text -noout

Отпечаток, по нему сертификат ищется в хранилище Windows:

    openssl x509 -in ca.crt -noout -fingerprint -sha256

Сгенерировать самоподписанный для опытов:

    openssl req -x509 -newkey rsa:2048 -nodes -days 365 ^
      -keyout test.key -out test.crt ^
      -subj "/C=RU/O=Librium/CN=Librium CA" ^
      -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"

Обратите внимание на форму записи subject через слэши, это та же самая
DN из раздела 1, только в синтаксисе openssl.
