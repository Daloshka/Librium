# Трафик приложений и кастомные WebSocket-протоколы

## С чего начать разбор незнакомого соединения

Выбери WebSocket в истории и нажми **Исследовать содержимое**. Сводка вручную просматривает всю сохранённую запись соединения, независимо от текущей страницы, строки поиска и фильтров сообщений. Для каждой группы показаны количество, отправленные и полученные сообщения и до двух первых примеров каждого направления. Пример открывает исходный сохранённый пакет, включая старые записи вне текущей страницы.

Группы описывают признаки содержимого: корректные конверты JSON-RPC 2.0, текстовые заголовки Socket.IO EVENT / ACK, CDP-подобный JSON, другие значения JSON, текст UTF-8 и бинарные данные. В пакетном JSON-RPC достаточно одного корректного конверта для этой группы; другие элементы могут оказаться неверными. Пример сохраняет индекс первого корректного элемента для последующего поиска пары. CDP-подобная форма сама по себе не устанавливает использование DevTools.

Совместимость BINARY с UTF-8 — отдельный признак, который не доказывает текстовый протокол: некоторые управляющие или двоичные значения тоже допускают такое декодирование. Произвольные байты не объявляются MessagePack или Protobuf. Для них сводка предлагает Hex, сравнение пакетов и явный выбор декодера по известному формату. Пустые, служебные кадры и CONTINUATION учитываются отдельно. Неполные прикладные данные и несогласованные размер, Base64 или направление не используются для распознавания полного конверта.

Для BINARY проверяются базовые признаки заголовков gzip и zlib с начала пакета. Это только подсказка: корректность сжатого потока и контрольной суммы подтверждается отдельной распаковкой. Открытие примера выбирает Hex и соответствующий кодек, но **Распаковать диапазон** нужно нажать вручную. Подсказка применяется только к тому открытию инспектора, которое запущено из примера: запоздавшая загрузка не меняет кодек после закрытия или повторного открытия пакета. Смещение по умолчанию — начало сообщения. Raw DEFLATE и другие форматы по произвольным байтам не угадываются. Основание проверяемых полей: [RFC 1952](https://www.rfc-editor.org/rfc/rfc1952.html) и [RFC 1950](https://www.rfc-editor.org/rfc/rfc1950.html).

Одно сообщение попадает ровно в одну группу; сначала отделяются служебные кадры, неполные и пустые данные, затем признаки сжатия BINARY, известные конверты, JSON и остальные байты. Поэтому сумма групп равна количеству сообщений, но не числу отдельных команд в пакетном JSON-RPC. **Обновить** создаёт свежий снимок, включая новые сообщения. Группировка ничего не отправляет в приложение и не изменяет архив.

API: `GET /api/traffic/{id}/ws-profile` с `x-librium-token`. Ответ: `id`, метаданные `summary`, `total`, граница `through` по ID сообщений и список `groups`. Группа содержит `kind`, `count`, `sent`, `received`, `unknown` и ограниченные `examples` с исходным ID, направлением, типом и необязательным индексом элемента JSON-RPC. Тела и Base64 в результат не включаются. Соединение проверяется по записи истории и WS-сессии; отсутствующий ID возвращает 404. Все счётчики и примеры относятся к одному read-only снимку SQLite через общий лимит WS-чтений.

## Все сообщения выбранной группы содержимого

В **Исследовать содержимое** нажми **Показать группу**. Откроются все сообщения этой группы в исходном соединении, а не только примеры. Прежние текстовый поиск, точное условие, тип кадра и направление снимаются, чтобы группа не оказалась случайно скрыта. Поиск использует свежий снимок записи; новые сообщения после сводки могут изменить счётчик.

Режим **Группа содержимого** доступен и в обычном поиске WS. Выбери группу в отдельном списке; направление и тип кадра можно затем ограничить вручную. Фильтрация выполняется по всему архиву до пагинации, поэтому старые сообщения находятся за сотнями более новых пакетов других типов. **Раньше** листает группу, а изменение условий возвращает к новым результатам.

**Найти во всех соединениях** переносит группу в общий поиск по архиву. Там можно добавить источник, окно / поток и URL. Для выхода из группировки выбери обычный формат поиска. Список показывает понятные названия групп; служебные идентификаторы вводить не нужно.

Открытие результата выбирает подходящий вид и сохраняет индекс первого корректного конверта JSON-RPC, когда это применимо. У признаков gzip / zlib выбирается Hex и подсказка кодека, но распаковка по-прежнему запускается вручную. Классификация совпадает со сводкой: совместимость BINARY с UTF-8 и заголовки сжатия остаются признаками, а не подтверждением формата.

API: обычные маршруты поиска соединения и всего архива с `{"format":"content_kind","search":"binary"}`. Допустимые группы: `json_rpc`, `socket_io`, `cdp_like`, `json`, `text`, `binary_utf8`, `binary`, `gzip_header`, `zlib_header`, `empty`, `incomplete`, `control`. Пустая или неизвестная группа отклоняется с 400. Сообщения результата получают аннотацию `content_kind`, а для группы JSON-RPC — `rpc_entries` с индексом первого корректного элемента. Отдельное чтение исходного сообщения и JSONL не добавляют эти аннотации; экспорт соединения остаётся полным и не ограничивается группой просмотра.

## Структурный поиск JSON-RPC

В поиске сообщений выбери **JSON-RPC: метод** или **JSON-RPC: точный ID**. Эти режимы доступны как для выбранного соединения, так и в **Поиске WS** по всему архиву. Они проверяют каждый корректный элемент JSON-RPC 2.0 внутри полного TEXT / BINARY, включая пакетные массивы; вложенный `id` или похожий текст в обычном JSON совпадением не считаются.

Метод ищется по подстроке с учётом регистра. Пустой запрос выбирает все команды и уведомления с методом, исключая ответы. ID вводится как JSON: `17` — число, `"17"` — строка, `null` — нулевой ID. Пустой запрос выбирает все корректные элементы с ID, включая `null`, и исключает уведомления без ID. Поиск `null` не означает возможность надёжно связать такие сообщения в пару.

Числа сравниваются без округления: `17`, `17.0` и `170e-1` обозначают один числовой ID. Строки сравниваются по полному декодированному значению; строковый и числовой ID не смешиваются. Поддерживаются большие целые, дроби, экспоненты, пустые и Unicode-строки. Неверные литералы, логические значения, массивы и объекты отклоняются с пояснением. Лимит литерала ID — 64 КиБ UTF-8; длинный ID передаётся через POST, без помещения в URL.

Из результата сопоставления команды и ответа нажми **Найти этот ID во всех соединениях**, чтобы открыть общий поиск с тем же типом и полным значением ID. Результат поиска открывается в режиме JSON-RPC. Индекс первого совпавшего элемента сохраняется для следующего поиска пары, поэтому пакет с несколькими разными ID не переключается на первый посторонний элемент. Если совпало несколько элементов, исходный пакет содержит их все.

Для API поиска соединения используй `POST /api/traffic/{id}/ws-search`, для всего архива — `POST /api/ws-archive-search`. Форматы: `jsonrpc_method` и `jsonrpc_id`; например, `{"format":"jsonrpc_id","search":"\"17\""}` для строкового ID и `{"format":"jsonrpc_id","search":"17"}` для числового. Тип, направление, область и пагинация работают как в остальных форматах. Совпавшее сообщение получает массив индексов `rpc_entries` с нуля. Это аннотация результата: отдельное чтение исходного сообщения и JSONL-экспорт её не добавляют.

## Повторяющиеся поля конверта

В режимах **CDP / DevTools** и **JSON-RPC 2.0** повтор имени в объекте конверта или его объекте `error` помечается как неоднозначность. Например, `{"id":1,"id":2,"method":"Runtime.evaluate"}` не интерпретируется как команда с ID 2. Имена сравниваются после декодирования JSON-экранирования: `id` и `i\u0064` — один ключ; `id` и `Id` — разные.

Такой объект не участвует в точном структурном поиске, выборе пары команды и ответа или распознавании конверта в сводке содержимого. В пакетном JSON-RPC однозначные элементы обрабатываются отдельно с сохранением своих индексов; неоднозначный элемент исключается. Быстрый просмотр всего пакета сообщает о повторяющемся поле, а исходный JSON остаётся доступен через **Исходное** и Hex.

Проверка относится к конверту и объекту `error`. Содержимое `params`, `result` и `error.data` не переписывается; повторяющиеся ключи во вложенных прикладных данных не превращают однозначный ID конверта в другой ID. Запись, отдельное чтение сообщения и экспорт сохраняют исходные байты, включая повторяющиеся поля.

## Команда и ответ JSON-RPC 2.0

В инспекторе выбери **JSON-RPC 2.0** и нажми **Найти команду / ответ**. Поиск читает всю запись одного соединения, включая сообщения вне текущей страницы. Для пакетного JSON-RPC выбери нужный элемент массива в списке: ответ может стоять в другой позиции своего пакета. Переход по найденной ссылке открывает исходное сообщение и сохраняет индекс нужного элемента для следующего поиска пары.

Сопоставляются строки и числа без округления. Строка `"1"` отличается от числа `1`; числовые записи `1`, `1.0` и `10e-1` имеют один ID. Большие целые, дроби и экспоненты сравниваются в десятичном виде с исходной точностью, включая значения вне диапазона JavaScript. В списке длинные ID и методы сокращены; исходные данные доступны в пакете и через **Копировать вид**. Уведомления без ID не предполагают ответа. `null` не связывается автоматически: по спецификации он также используется в ответах с неизвестным ID.

Пара выбирается только при единственной команде, единственном ответе в обратном направлении и порядке записи «команда раньше ответа». Два встречных потока вызовов с одним ID рассматриваются отдельно. Повтор ID, несколько ответов или ответ, записанный раньше команды, дают неоднозначность; на предполагаемые последовательные пары такие записи не разбиваются. Время между записями показывается только для единственной пары при неубывающих часах, без заявления о сетевом RTT.

Поддерживаются полные TEXT и BINARY с корректным UTF-8 / JSON, один объект или пакет из 1–256 элементов. Неверный элемент пакета исключается отдельно с сохранением индексов остальных. Частичные сообщения, повторяющиеся ключи объекта протокола или ошибки, неверные `params`, тип ID, версия и структура ответа исключаются. Пакеты с превышенным лимитом целиком недоступны для сопоставления. Исходные байты, просмотр и экспорт не изменяются.

API: `GET /api/traffic/{id}/ws/{message_id}/jsonrpc-related`, заголовок `x-librium-token`. Необязательный `?entry=0` выбирает индекс элемента (с нуля); без него выбирается первый элемент с ненулевым ID. Ответ содержит список исходных `entries`, `selected`, тип и исходное значение ID, `command_count`, `response_count`, до 20 ссылок `commands` / `responses` с ID сообщения и индексом элемента, `status` (`matched`, `missing`, `ambiguous`) и время между записями, когда оно известно. `supported:false` объясняет, почему выбранный элемент не сопоставляется. Исчезнувший или чужой ID сообщения возвращает 404. Весь поиск выполняется в одном read-only снимке SQLite через общий лимит WS-чтений.

Основание правил: [спецификация JSON-RPC 2.0](https://www.jsonrpc.org/specification), разделы Request, Response, Notification и Batch.

## Соседние сообщения в соединении

Открой исходный пакет и нажми **Контекст соединения**. Окно показывает до пяти записанных сообщений перед ним и пяти после него: оба направления, включая PING / PONG / CLOSE. Выбранный пакет выделен, у каждой строки видны ID, время с миллисекундами, дата, тип, исходный размер и короткий фрагмент. Порядок определяется записью в архив, поэтому изменение системных часов его не переставляет.

**Предыдущее**, **Следующее** и **Открыть** загружают исходный сохранённый пакет в инспектор, сохраняя выбранный формат просмотра. Диапазон разбора и выделение исходного пакета при переходе сбрасываются. Соседние записи всегда относятся к тому же соединению; одинаковые URL и перемежающиеся ID других соединений их не смешивают. Фильтры поиска не применяются, и близость двух сообщений не считается доказательством пары запрос / ответ.

**Обновить** повторно читает контекст, включая сообщения, пришедшие после первого открытия. Закрытие или смена исходного пакета убирает прежний контекст; поздние ответы не заменяют новый просмотр. Окно доступно и для старых сообщений, которых нет на текущей странице истории.

API: `GET /api/traffic/{id}/ws/{message_id}/context`, заголовок `x-librium-token`. Ответ содержит `id`, `message_id`, `previous`, `next` (ближайшие ID или `null`) и до 11 коротких `messages` в порядке записи. Тела и Base64 в ответ не входят; полные байты читаются обычным API сообщения. Если ID не принадлежит указанному соединению или удалён, возвращается 404. Чтение использует один снимок SQLite и индекс соединения, не разбирая всю сессию.

## Поиск сообщений сразу во всех соединениях

Нажми **Поиск WS** в верхней панели. Он ищет по всему сохранённому архиву, включая старые соединения и переподключения лаунчера. Выбери формат содержимого, тип и направление сообщений. Область можно ограничить источником, подстрокой URL (без учёта регистра), а при выбранном окне или потоке — его точным контекстом. Окна с одинаковым названием остаются разными контекстами. Фильтры списка HTTP / WS в этот поиск не переносятся.

Кнопка **Найти во всех соединениях** рядом с поиском выбранного WebSocket переносит его условия: текст, JSON Pointer, точное значение JSON / Socket.IO, Hex-маску или точное поле протокола. Точное условие показано отдельной меткой. Нажатие метки или изменение содержимого, поля JSON либо формата снимает его; тип, направление и область можно менять с сохранением точного условия.

В результатах видны соединение, окно / поток, источник, направление, тип, исходный размер и короткий фрагмент сообщения. **Открыть** загружает исходный сохранённый пакет в инспектор. Для Hex, масок и полей протокола выделяется найденный диапазон исходных байтов. Фрагмент в таблице сокращён независимо от отметки о частичном сохранении исходного пакета.

Страница содержит до 100 результатов, новые сообщения идут первыми по порядку записи. Переходы **Назад / Далее** используют один снимок по ID сообщений: продолжающийся захват не сдвигает страницы. **Найти** начинает новый снимок с актуальными данными. Изменение условий убирает прежние результаты до нового поиска. Поиск читает архив; сообщения и трафик приложения не изменяются.

API: `POST /api/ws-archive-search` с `x-librium-token`. Например, `{"format":"hex_mask","search":"@2: 01 ?? ff","source":"cdp_node","url":"/socket"}`. Поддерживаются те же `search`, `kind`, `format`, `direction`, `pointer`, `exact`, `socketio_exact`, `field_exact`, что и в поиске соединения; дополнительно — `source`, `capture_context`, `url`. Ответ содержит `matches` с метаданными соединения и короткими превью сообщений, `total` в выбранной области, `matched`, `through`, `older`, `next_before`. Для следующей страницы передай неизменные условия, полученный `through` и `before: next_before`. Полные байты читаются отдельно по исходным ID через `/api/traffic/{exchange_id}/ws/{message_id}`.


В сводке **Значения поля** нажми **Найти точно**, чтобы открыть сообщения с выбранным скалярным значением. Совпадение учитывает тип, регистр и полное содержимое; строка `"1"` не совпадает с числом `1`, числовая запись `1` отличается от `1.0`. Фильтр применяется ко всей записи соединения до пагинации и сочетается с направлением и типом сообщений. Направление сначала переключается на оба, тип — на данные TEXT / BINARY.

Выбранное условие видно в метке **Точно**. Нажми её для снятия условия; ввод текста переключает поиск на подстроку. Смена поля, формата или соединения тоже снимает точное условие. Поддерживаются полные скалярные значения до 64 КиБ: они передаются в теле локального запроса поиска и не зависят от ограничения длины URL. Это чтение архива; трафик приложения и хранимые сообщения не изменяются.

Выбери **Поиск: поле JSON**, укажи путь (например, `/event`) и нажми **Значения поля**. Сводка показывает частые строки, числа, логические значения и `null` по всей записи выбранного WS-соединения, с количеством отправленных и полученных сообщений. Текущий текст поиска, тип сообщения и направление просмотра на сводку не влияют. Она обновляется вручную; захват продолжается.

Показывается до 100 самых частых значений. Счётчики охватывают весь архив, отдельно указаны сообщения с остальными значениями и исключённые записи. Группы учитывают тип и регистр: строка `"1"` отличается от числа `1`, `ready` от `Ready`. Числа группируются по точной исходной записи (`1` и `1.0` отдельно), строки — по декодированному содержимому. Отсутствующие или неоднозначные поля, объекты, массивы, неверный JSON / UTF-8 и частичные сообщения исключаются. В таблице значение сокращено до 160 символов; **Копировать** копирует его целиком. Это сводка значений, исходные сообщения и экспорт остаются неизменными.

Открой сообщение кнопкой **Открыть → Поля JSON**. Таблица показывает адрес, тип и короткое значение каждого поля, включая вложенные объекты и массивы. **Копировать путь** копирует готовый адрес; **Найти поле** закрывает просмотр, выбирает исходное WS-соединение и включает поиск наличия этого поля во всём его архиве. Затем можно ввести нужное значение в строку поиска. Направление переключается на оба, тип — на данные TEXT / BINARY.

Структура читается из полного исходного сообщения, без диапазона или распаковки. Показывается до 256 значений, до 64 уровней вложенности и до 2048 байт в пути; ограниченный список помечается. Числовые значения сохраняют точную исходную запись. Повторяющийся ключ показывается один раз с отметкой неоднозначности; поиск для него отключён. Неполные сообщения недоступны для этого просмотра. Таблица и переход к поиску не изменяют байты, JSONL или хранимые сообщения.

При быстром вводе фильтра просмотр отправляет до двух поисковых запросов одновременно и сохраняет только последний ожидающий вариант. Когда освобождается место, запускается актуальный поиск; промежуточные варианты не накапливаются в очереди ядра. Ожидающий запрос повторно проверяется перед отправкой: после паузы, смены соединения или возврата к уже выполняющемуся поиску устаревший вариант отбрасывается. Результаты и ошибки ранее отправленных запросов применяются только к соответствующим текущим условиям просмотра.

Поиск WS, сводка и поиск пары CDP читают отдельный снимок базы: длительный разбор архива не удерживает общую блокировку захвата. Счётчики, сообщения и признак старых страниц внутри одного ответа относятся к одному состоянию базы; новые сообщения появятся при следующем обновлении. Одновременно выполняются до двух таких чтений. Если таймер обновления и ручной просмотр запрашивают одинаковый поиск, пока он ещё выполняется, используется один запрос; после завершения следующее обновление снова читает свежие данные.

Для собственного JSON-протокола выбери **Поиск: поле JSON**. В соседнем поле укажи путь, например `/event`, `/params/state` или `/items/0/type`; в обычной строке поиска — нужное значение. Проверяется подстрока без учёта регистра только внутри выбранного значения. Пустой поисковый текст означает «поле существует», включая `null` и пустую строку; отсутствующий путь не совпадает. Пустой путь означает весь JSON-документ. Фильтр применяется ко всей истории соединения до пагинации и сочетается с типом и направлением сообщений.

Путь использует [JSON Pointer (RFC 6901)](https://www.rfc-editor.org/rfc/rfc6901.html): `/items/0` — первый элемент массива, `~1` означает `/` внутри имени ключа, `~0` — `~`. Имена ключей учитывают регистр; URI-пути с `#` не принимаются. Лимиты пути — 2048 байт UTF-8 и 64 части. Если указанный ключ встречается в объекте несколько раз, значение не угадывается и такая запись не совпадает.

Учитываются только полные исходные TEXT / UTF-8 BINARY сообщения с корректным JSON. Строки декодируются, числа и остальные значения ищутся в исходной JSON-записи без округления (это текстовый поиск, а не числовое сравнение). Для объектов и массивов поиск идёт по исходному JSON выбранного поддерева. В карточке показаны путь и первые 160 символов найденного значения; они также попадают в копируемый вид. Форматированный вид WebSocket JSON также сохраняет исходную запись чисел, включая длинные ID, точные дроби и экспоненты. В старых браузерах без поддержки точного форматирования чисел показывается исходный JSON. Байты, отдельный просмотр сообщения и JSONL остаются исходными.

В поиске сообщений доступны **CDP: метод / событие** и **CDP: точный ID**. Первый ищет подстроку в поле `method` с учётом регистра (например, `Runtime.evaluate` или `Runtime.console`), включая события без ID. Второй ищет числовой ID команды, результата или ошибки целиком: `17` не совпадает с `117`, числом в параметрах или строкой в тексте. Ведущие нули в запросе допустимы (`0017` означает `17`); дроби, отрицательные значения и числа больше `9007199254740991` отклоняются до запроса из интерфейса и на API.

Непустой запрос CDP обрабатывается по всей истории выбранного соединения до пагинации, сочетается с направлением и типом сообщения и автоматически включает просмотр **CDP / DevTools**. Учитываются полные исходные TEXT и UTF-8 BINARY сообщения корректной структуры CDP; JSON-RPC, вложенные одноимённые поля и частичные сообщения не подмешиваются. Пустой запрос сохраняет обычный режим показа всех сообщений. При поиске по ID могут находиться записи разных `sessionId` одного соединения; для сопоставления пары используй кнопку в отдельном просмотре.

Для локального CEF-моста Morphius выбери **WS: CDP / DevTools** в панели сообщений или **CDP / DevTools** в отдельном просмотре. Для JSON-RPC выбери отдельный режим **JSON-RPC 2.0**. Разбор показывает команду, уведомление / событие, результат или ошибку, ID и CDP `sessionId`; JSON-RPC поддерживает пакеты до 256 элементов. Режим выбирается явно: обычный JSON автоматически не объявляется протоколом DevTools. Для CDP доступен отдельный поиск пары команды и ответа; JSON-RPC пока разбирается по отдельным сообщениям.

Числовой ID JSON-RPC выводится из исходной записи числа, включая значения за пределами точности JavaScript. Под сводкой остаётся исходный JSON без перезаписи чисел и полей; **Копировать вид** копирует сводку вместе с ним. **Сохранить байты** и JSONL продолжают сохранять оригинал. Неполные сообщения, неверные объекты и невалидный UTF-8 бинарных данных показывают причину отказа; при явном выборе полного известного диапазона бинарного сообщения разбирается только этот диапазон. Формат также доступен в отдельном распакованном представлении.

В отдельном просмотре исходного сообщения выбери **CDP / DevTools → Найти ответ / команду CDP**. Поиск читает всю сохранённую WS-сессию независимо от фильтров и страницы: сравнивает числовой ID и `sessionId`, ищет команду и ответ во встречных направлениях. Отсутствующий `sessionId` отличается от пустой строки. Единственная пара определяется только при одной команде и одном последующем ответе; повторы ID, несколько ответов и обратный порядок помечаются как неоднозначность. Можно открыть кандидата и перейти обратно. Время между записями показывается только для единственной пары при неубывающих временных метках; это время наблюдения, а не измерение сети.

Поиск выполняется вручную по отдельному снимку базы и не удерживает блокировку записи захвата. Подсчитываются все кандидаты, показываются первые 20 команд и 20 ответов. Если ответ ещё не пришёл, повтори поиск. Учитываются только полные исходные TEXT / UTF-8 BINARY сообщения с безопасным целым CDP ID; события без ID не имеют пары. Производные диапазоны и распакованные данные в поиске пары не участвуют.

Описание форматов: [Chrome DevTools Protocol](https://chromedevtools.github.io/devtools-protocol/), [JSON-RPC 2.0](https://www.jsonrpc.org/specification).

В истории и заголовке выбранного запроса показывается **WS · клиент** или **WS · сервер**. Роль относится к наблюдаемому приложению: оно подключилось к другому серверу либо приняло входящее соединение. Фильтр **Все роли WS → WS: клиент / WS: сервер / WS: роль неизвестна** применяется ко всей базе до разбиения на страницы и сочетается с источником, статусом, поиском и правилами. При выборе роли остаются только WS-записи; например, условие «HTTP» вместе с ролью WS даст пустой результат. Роль сохраняется в сессии фильтров и убирается своей меткой или кнопкой «Сбросить всё».

Новые записи прокси и клиентских источников Chromium / Node.js помечаются как `client`, новые принятые соединения сервера ws — как `server`. Роль клиента сохраняется и у неудачной или ещё не завершённой попытки рукопожатия; успешность видна по статусу отдельно. Старые записи и адаптеры без явной метки остаются с неизвестной ролью: сторона не угадывается по адресу или служебным заголовкам. Адреса `ws:` / `wss:` учитываются как WS-попытки даже без заголовков рукопожатия; при обновлении такие старые записи включаются в WS-фильтры без назначения им клиентской или серверной роли. Роль доступна в данных запроса, сводке и JSONL как необязательное `summary.ws_role` (`client` / `server`).

Захват главного процесса поддерживает также новые входящие соединения **WebSocketServer из пакета ws**, включая ручной `noServer` / `handleUpgrade`, используемый локальным CEF-мостом Morphius. Первые синхронные ответы сервера записываются до возврата в обработчик приложения. URL берётся из принятого запроса, для TLS используется WSS; сохраняются фактические заголовки запроса и окончательные заголовки ответа после обработчиков приложения. Служебный заголовок `x-librium-ws-role` показывает `server` или `client`. Для сервера «отправлено» означает ответ приложения внешнему клиенту, «получено» — входящую команду. Разные клиенты на одном URL сохраняются отдельными соединениями. Уже принятые до установки наблюдателя серверные соединения нужно переподключить; их неизвестный путь рукопожатия не угадывается.

По текущим исходникам Morphius авторизация, список серверов и загрузки используют HTTP-запросы. Его локальные WebSocket-мосты CEF передают команды DevTools; наличие такого WS не означает, что игровой сервер общается по этому же протоколу. Для захвата нужны соответствующие источники приложения: HTTP главного процесса, WebSocket его моста либо сетевые события окна. Новый режим не превращает нативный игровой TCP/UDP или `alt.emit` во входящий WebSocket.

Если BINARY содержит сжатую полезную нагрузку, открой сообщение, укажи начало и при необходимости длину сжатого участка, выбери **gzip**, **zlib** или **DEFLATE без заголовка** и нажми **Распаковать диапазон**. Используются текущие значения полей; применять обычный разбор перед распаковкой не нужно. Результат открывается в отдельном окне с Авто / JSON, MessagePack, Protobuf и Hex. **Копировать вид** копирует выбранное представление результата. **Сохранить распакованные байты** создаёт отдельный `.bin` с точным результатом распаковки, без форматирования декодера и без добавленного BOM. Имя включает исходные ID, кодек, начало и длину сжатого участка. В настольной версии диапазон повторно читается из истории перед выбором файла, поэтому после удаления источника сохранение сообщает об ошибке. Отмена диалога не меняет существующий файл; замена выполняется после записи временного файла. Начатая запись завершается перед выходом из приложения. В браузере скачивается проверенный результат из открытого окна. Его смещения начинаются с нуля и относятся к распакованным данным. Исходное сообщение, его сохранение, поиск, экспорт и сравнение байтов остаются сжатыми.

Формат выбирается явно. Вход и результат ограничены 64 КиБ; превышение лимита, повреждение, неполный поток или лишние байты дают ошибку без частичного результата. gzip поддерживает несколько последовательных gzip-частей; zlib и raw DEFLATE требуют один законченный поток. Для частично сохранённого исходного сообщения нужно явно задать длину полностью доступного сжатого участка; полнота всего исходного пакета при этом не предполагается. Это распаковка полезной нагрузки сообщения, а не реализация расширения WebSocket `permessage-deflate`: потоки с общим словарём между сообщениями, шифрование и вложенные слои автоматически не снимаются. До явного сохранения ограниченный результат остаётся только в памяти открытого окна; закрытие исходного инспектора закрывает и его.

Для изучения бинарного заголовка открой сообщение и разверни **Числа с байта…**. Поле **Смещение → Перейти** выбирает начало чтения в исходном пакете; при открытии из поиска используется начало найденного совпадения. Таблица показывает варианты uint/int на 8, 16, 32 и 64 бита, float32 и float64 в LE (младший байт первым) и BE (старший байт первым). Все варианты читаются с одной позиции, каждый — на свою ширину. 64-битные целые показаны без потери точности; `-0`, `NaN` и бесконечности сохраняются в числовом представлении. `—` означает, что для типа не хватает сохранённых байтов: недостающий хвост не дополняется нулями. **Копировать числа** копирует таблицу с исходным смещением и отметкой частичного сообщения. Это варианты интерпретации, а не определение схемы протокола. Диапазон разбора не сдвигает эту таблицу; архив, сравнение и экспорт не меняются. При открытии другого сообщения панель снова сворачивается.

Для BINARY с известным заголовком открой сообщение, выбери MessagePack, Protobuf или Авто / JSON и укажи **Разбор с байта**, например `12` или `0x000c`, затем нажми **Применить**. Необязательная **Длина** задаёт размер участка в байтах и тоже принимает десятичное или Hex-число. Пустая длина означает до конца. Это позволяет разобрать полезные данные между заголовком и хвостом пакета; границы и назначение полей автоматически не угадываются. Начало должно быть внутри сохранённых байтов, длина — положительной и не выходящей за их пределы. **Весь пакет** возвращает начало 0 и пустую длину.

Диапазон действует только для открытого сообщения и сбрасывается при открытии другого. Hex, исходное представление, поиск, сохранение, экспорт и сравнение продолжают использовать весь пакет; копирование вида копирует результат декодирования. Смещения полей Protobuf отсчитываются от выбранного начала. Если длина не задана, усечённое сообщение по-прежнему не разбирается как MessagePack / Protobuf. При явно заданной длине разбирается только полностью сохранённый выбранный участок, в том числе внутри усечённого сообщения: это не подтверждает полноту исходного пакета, что отдельно указано рядом с результатом. Нулевую длину, пустое сообщение и диапазон за пределами сохранённого префикса применить нельзя.

В списке типов WebSocket можно выбрать **Данные: TEXT / BINARY** или **Служебные: PING / PONG / CLOSE**, а также отдельный тип. Группа применяется ко всей сохранённой сессии до разбиения на страницы и сочетается с поиском и направлением. Так сообщения приложения можно найти даже за длинной последовательностью keepalive-кадров. Классификация использует тип WebSocket, а не содержимое: heartbeat Engine.IO, переданный как TEXT, остаётся в группе данных; отдельные CONTINUATION, полученные от внешнего источника, остаются в «Все сообщения». Сводка и экспорт JSONL по-прежнему охватывают всю сессию независимо от фильтра. В низком окне область инспектора прокручивается, чтобы развёрнутая панель фильтров не делала сообщения недоступными.

Для сравнения двух сообщений открой первое и нажми **Выбрать образец**, затем открой второе и выбери **Сравнить с образцом**. Окно показывает число совпавших и отличающихся байтов в общей сохранённой части, а также подтверждённые байты только в A или B (за концом другого сообщения). Байты напротив несохранённого фрагмента учитываются отдельно как недостаточные данные, а не как разница длины. Отличия сгруппированы в участки; кнопки **← Участок / Участок →** и поле смещения позволяют просмотреть их все. Для выбранного смещения показывается окно до 256 байтов с Hex и ASCII обоих образцов. Сравнение выполняется по одинаковым смещениям, без выравнивания сдвинутых данных или угадывания полей протокола. `??` означает, что байты не сохранены в усечённой записи, `--` — байты за полным размером сообщения, даже если оно усечено. Синие байты напротив `??` нельзя сравнить; жёлтые подтверждённо находятся за концом другого сообщения. Неизвестные байты не считаются изменёнными. Участки, где с обеих сторон нет сохранённых байтов, не показываются и не сравниваются; совпадение сохранённых префиксов не означает равенства полных пакетов. Образец хранится только в памяти текущего окна: **Сбросить образец**, очистка истории в этом окне или закрытие Librium его удаляют. Сравнение не меняет сообщения и не отправляет их клиенту или серверу.

Кнопка **Создать поле B** переносит смещение и полную длину выбранного участка сравнения в редактор полей текущего сообщения. Предлагается `bytes`; имя остаётся пустым, назначение и тип поля не угадываются. Задай имя, при необходимости выбери числовой тип или UTF-8, затем нажми **Добавить поле**. До этого схема не изменяется; сохранение на устройстве выполняется отдельной кнопкой **Сохранить схему**. Существующие поля черновика остаются на месте. После добавления доступны **Значения** по всей сессии, **Найти точно** и сравнение именованных полей с образцом. Кнопка недоступна на совпадающих смещениях, для управляющих сообщений и если участок B не сохранён целиком. Неизвестные байты A не мешают описать сохранённый участок B. Смещения относятся к исходному пакету, независимо от выбранного диапазона декодера или распаковки.

В окне сравнения **Копировать участок A / B** копирует исходные байты всего выбранного участка в виде Hex с пробелами, даже если часть участка находится за пределами окна из 256 байтов. Выбор участка — кнопками ← / → или смещением внутри него. На совпадающем смещении эти действия недоступны. **Открыть A / B в Hex** открывает соответствующее сообщение из архива и выделяет весь участок; для образца из другого соединения открывается именно его исходное сообщение. Если байты стороны не сохранены, её кнопки недоступны. Образец в памяти можно скопировать даже после удаления его сообщения вне этого окна; переход к удалённому сообщению покажет ошибку архива. Копирование не включает номера сообщений, маркеры `??` / `--`, заголовки или ASCII; исходные данные и фильтры ленты не меняются.

Кнопка **Открыть** у сообщения показывает его отдельно от ленты. В Hex доступны все сохранённые байты — до 64 КиБ / 4096 строк, даже если совпадение не попало в общий предпросмотр. При открытии результата поиска по байтам окно переходит к первому совпадению и подсвечивает его в Hex и ASCII. Поле **Смещение** принимает десятичное число или Hex с `0x`; **Выделить** показывает заданный диапазон, а **К совпадению** возвращает к результату поиска. Переход за пределы сохранённого фрагмента отклоняется. Поле **Длина** задаёт число выделенных исходных байтов (десятичное число или Hex); пустое поле означает 1 байт. Нажми **Выделить**, чтобы применить смещение и длину: весь диапазон подсвечивается в Hex и ASCII. Неверные границы не меняют ранее применённое выделение. **К совпадению** возвращает и смещение, и полную длину найденного шаблона. **Копировать выделение** копирует все байты применённого выделения как Hex с пробелами, без адресов и ASCII. **Поле из выделения** открывает редактор с этим смещением, длиной и типом bytes; имя и добавление поля остаются за пользователем. **Найти на этом смещении** ищет точные исходные байты последнего применённого выделения на той же позиции во всей записи этого соединения. Длина и значение передаются в POST, до 64 КиБ выделения, без переноса Hex в URL и без создания / сохранения поля схемы. Поиск переключается на TEXT / BINARY обоих направлений; затем направление можно сузить. Условие видно отдельной плашкой, которую можно снять; **Открыть** у результата восстанавливает полную длину выделения. Совпадение со сдвигом не учитывается; для поиска в любом месте остаётся обычный Hex. Для управляющих кадров доступно копирование, но не схема полей или поиск выделения; у пустого сообщения эти действия недоступны. Выделение не меняет диапазон декодера, исходные данные или сохранение всего пакета. После изменения полей формы сначала нажми **Выделить**: копирование и создание поля используют последнее применённое выделение. В том же окне можно выбрать декодер, скопировать представление или сохранить исходные байты. Для декодированного текста остаётся лимит отображения 3000 строк; исходные данные доступны через Hex и сохранение. Если запись удалена или загрузка не удалась, окно сообщает об этом и предлагает повторить загрузку. Само открытие сообщения не отправляет данные в приложение и не повторяет сетевой запрос клиента.

Режим **Поиск: байты (Hex)** ищет точную последовательность в исходных байтах всех типов WS-сообщений, независимо от текстового представления или декодера. Примеры: `00 ff 2a` и `00FF2A` означают одни и те же три байта. Допускаются пары цифр `0–9`, `a–f`, без `0x`, масок и разделителей кроме пробелов / ASCII-переводов строк. Нечётный или неверный запрос помечается рядом с полем; пустой запрос снимает ограничение по байтам. Поиск выполняется во всей записанной сессии до разбиения на страницы, совместно с фильтрами направления и типа. Представление переключается на Hex, а заголовок найденного сообщения показывает смещение первого совпадения от начала содержимого, например `0x00000f`. В усечённых сообщениях проверяются только сохранённые байты; совпадение за пределами фрагмента не предполагается. Поиск не меняет архив и не добавляет смещения в JSONL-экспорт.

Режим **Поиск: Hex с маской** ищет шаблон в исходных байтах всей записанной сессии. `01 ?? ?? ff` означает байт `01`, два любых сохранённых байта и `ff`. `??` всегда занимает ровно один байт; половины байта (`a?`), `*`, диапазоны и регулярные выражения не поддерживаются. Пары можно писать слитно или разделять ASCII-пробелами / переводами строк. Максимум — 256 байтов шаблона, включая `??`. Чтобы проверять только одну позицию, добавь префикс: `@12: 01 ?? ff` или `@0x0c: 01 ?? ff` — строго с байта 12 исходного сообщения. Смещение — от 0 до 65535; маска вместе со смещением должна помещаться в первые 64 КиБ. Без префикса остаётся поиск в любом месте. Префикс без маски недопустим. Обнаруженное смещение и подсветка остаются абсолютными, относительно начала исходного сообщения, независимо от диапазона декодера. Шаблон только из `??` находит сообщения с достаточным числом сохранённых байтов; пустой шаблон снимает ограничение по байтам. Тип и направление фильтруются до разбиения на страницы. Совпадение должно целиком находиться в сохранённой части: `??` не восстанавливает неизвестный хвост и не пересекает границы сообщений. Поиск работает и с TEXT / управляющими сообщениями, используя их реальные байты. Результат показывает смещение первого совпадения; **Открыть** выделяет весь шаблон в Hex, включая позиции `??`. Поиск не меняет данные, схемы и JSONL-экспорт и не распаковывает содержимое. Для длинной точной последовательности остаётся обычный режим Hex.

Кнопка **Сигнатуры** открывает именованные настройки бинарного поиска. Если активен обычный Hex или Hex с маской, текущая строка, тип и направление переносятся в форму; для других режимов маска остаётся пустой. Задай имя и непустую маску, нажми **Сохранить**. В текущем профиле приложения / браузера можно хранить до 20 сигнатур с именами до 64 символов. В другом WebSocket открой **Сигнатуры**, выбери сохранённое имя и нажми **Применить к этому WS**: включится Hex-поиск с маской с сохранёнными типом и направлением, по всей записи выбранного соединения. Применение не сохраняет правки формы, отправку сообщений не выполняет и прежнее соединение не выбирает. Сохраняются только `name`, `pattern`, `kind`, `direction`; ID, адрес, другие сообщения и данные аккаунта не добавляются. Маска сама содержит введённые пользователем байты и записывается только явной кнопкой сохранения.

Для замены сначала выбери сигнатуру в списке, затем сохрани с тем же именем. Совпадение с именем другой сигнатуры не перезаписывает её. **Удалить выбранную** удаляет выбранную запись, оставляя её настройки в форме. Ошибка чтения, неподдерживаемая версия или ошибка записи не стирают прежние данные. Сигнатуры можно применять без сохранения; смена выбранного соединения закрывает редактор и сбрасывает несохранённую форму.

В меню **Вид сообщений WebSocket** можно выбрать **Общий поток**: отправленные и полученные сообщения идут одной лентой в порядке записи, с подписью направления и цветной полосой. Это помогает читать последовательность обмена; Librium не назначает сообщению «ответ» по одному только времени. Порядок соответствует ID записей, даже если часы или временные метки меняются. Фильтры, переход к старым сообщениям, декодер и сохранение байтов работают в обоих видах. **Копировать** копирует сообщения текущей страницы обоих направлений в общем потоке. Выбор вида сохраняется между запусками. Для просмотра HTTP-рукопожатия нажми соответствующую вкладку — интерфейс вернётся к двум панелям. **По направлениям** оставляет отдельные панели отправленных и полученных сообщений.

У каждого WS-сообщения есть кнопка **Сохранить байты**. Она сохраняет содержимое из архива без временной метки, номера сообщения и форматирования декодера: текст — в `.txt` без добавленного BOM, остальные типы — в `.bin`. Для усечённых сообщений кнопка называется **Сохранить фрагмент**, а имя содержит `-partial`: файл включает только доступные байты, недостающие данные не восстанавливаются. В настольном приложении путь выбирается системным диалогом; отмена не меняет файл, замена выполняется после успешной записи. В браузере используется обычное скачивание. Сообщение читается по ID внутри выбранного соединения, поэтому можно сохранить и старую запись, найденную поиском. Если история уже очищена, сохранение сообщает об ошибке. Для всей сессии остаётся экспорт JSONL.

Кнопка **Сводка** показывает снимок всей записанной WS-сессии: число сообщений и их объём в каждом направлении, реально сохранённые байты, число усечённых сообщений, типы сообщений и время первого / последнего сообщения. Фильтры и текущая страница на сводку не влияют. **Обновить сводку** пересчитывает её вручную; захват продолжает работать, в том числе во время паузы просмотра. Объём относится к содержимому записанных сообщений и не включает сетевые заголовки; это не общий расход сети приложения. Байтовые суммы и единицы в интерфейсе округляются. Отсутствующие до начала захвата сообщения в сводку не входят. Расчёт выполняется только по запросу, без полного сканирования истории при каждом автоматическом обновлении панели.

В сводке таблица **Интервалы одного направления и типа** показывает минимальный, средний и максимальный промежуток в миллисекундах между соседними записанными сообщениями каждой пары направления / типа. Используется порядок захвата (ID), а не сортировка по времени. TEXT и BINARY, DATA и управляющие кадры, отправка и приём не смешиваются. Усечённое содержимое не мешает учитывать временную метку. Нулевые промежутки входят в среднее и посчитаны отдельно; они могут быть следствием разрешения часов, а не одновременной отправки. Отрицательные промежутки исключены из минимума / среднего / максимума и показаны как «Часы назад». У одного сообщения интервалов нет: вместо времени показано «—». Расчёт охватывает всю сессию и игнорирует фильтры ленты. Это наблюдаемые интервалы захвата, не RTT, не задержка сети и не подтверждение heartbeat.

Под максимальным интервалом кнопки **До / После** открывают исходные сообщения по его краям. Это соседние сообщения внутри одной пары направления / типа; другие сообщения могут находиться между ними. При равенстве максимумов выбирается первая пара в порядке захвата. Ссылки вычисляются по всей записанной сессии и открывают старые сообщения вне текущей страницы или фильтра, сохраняя фильтры ленты. У одиночного сообщения и при отсутствии неотрицательных интервалов ссылок нет; нулевой максимум имеет действительную пару. До ручного обновления сводки ссылки относятся к её снимку. Если запись удалена из архива, инспектор показывает ошибку загрузки и возможность повтора. Потерянные до захвата пакеты и нерегулярная доставка наблюдателем могут менять картину.

Для бинарного сообщения можно вручную выбрать **WS: Protobuf (без схемы)**. Просмотр показывает смещение и номер каждого поля, тип записи (`VARINT`, `I64`, `LEN`, `SGROUP`, `I32`), varint как точную десятичную строку, фиксированные значения и поля с длиной как Hex; для `LEN` дополнительно выводится UTF-8, если байты корректны. Повторяющиеся поля и их порядок сохраняются. Это разбор [формата передачи Protobuf](https://protobuf.dev/programming-guides/encoding/), а не восстановление `.proto`: имена полей, signed / ZigZag, bool / enum, float / double и назначение `LEN` не угадываются. Вложенные сообщения и packed-массивы внутри `LEN` остаются байтами. В режиме **Поиск: Protobuf** запрос проверяется по разобранным значениям во всей истории до разбиения на страницы, совместно с фильтрами типа и направления. Повреждённые и усечённые сообщения не дают совпадений в таком поиске; без поискового текста они видны с пояснением. Ограничения: 64 КиБ, 10000 полей и 64 уровня групп. Контейнеры, сжатие, gRPC-обрамление и шифрование автоматически не снимаются. Исходные байты и JSONL-экспорт остаются без преобразований.

Прокси пересылает PING, PONG и CLOSE между клиентом и сервером, без собственных автоматических ответов. Самостоятельный PONG также передаётся и сохраняется. Фрагменты TEXT / BINARY проходят в исходном порядке, включая управляющие кадры между ними; для просмотра в истории они собираются в логическое сообщение. Символ UTF-8 может пересекать границу фрагментов. Сохраняются первые 64 КиБ и полный размер сообщения; предел передачи — 16 МиБ на кадр и 64 МиБ на логическое сообщение. Незавершённые фрагменты не выдаются за полное сообщение. Сжатие `permessage-deflate` прокси не согласовывает; для наблюдения сообщений после распаковки можно использовать захват приложения.

Прокси завершает оба направления WebSocket: после нормального окончания одного направления он ждёт второе до 5 секунд, чтобы сохранить ответный CLOSE-кадр. Ошибка передачи завершает соединение сразу; истечение ожидания сохраняется как ошибка. В сводке закрытия показан первый наблюдаемый CLOSE-кадр, а ответный доступен среди сообщений с соответствующим направлением. События встроенного Node.js WebSocket / библиотеки `ws` дают итоговый код и причину без направления кадра.

При WSS проверяются сертификат и имя целевого сервера по корням WebPKI. Доверие клиента к CA Librium не отключает эту проверку. Ответ отказа HTTP, например 403, сохраняет исходный статус и тело; неподтверждённое рукопожатие не превращается в открытую WebSocket-сессию.

Кнопка **Пауза** останавливает автообновление списка, деталей запроса и WS-сообщений. Захват и сохранение трафика продолжаются. Во время паузы можно вручную менять фильтры, выбирать запросы и переходить по страницам; **Продолжить** возвращает автообновление и показывает новые записи. Ответы на автоматические запросы, отправленные до паузы, больше не меняют просмотр.

В панели сообщений сохраняются **код закрытия** и **причина**, если источник их сообщает. Для Node.js доступны события закрытия встроенного WebSocket и библиотеки `ws`; для прокси — наблюдаемый CLOSE-кадр с кодом и направлением «отправлено» / «получено». Значение 1006 означает закрытие без подтверждённого CLOSE-кадра, а не код, переданный по сети. Отключение захвата или закрытие CDP не подменяется кодом закрытия сервера. Chromium CDP не сообщает эти поля в событии закрытия; старые записи также могут их не содержать. Данные доступны после перезапуска Librium и входят в строку `session.close` экспорта JSONL как `{code, reason}` с необязательным `direction` (`sent` / `received`) для наблюдаемого кадра; при отсутствии сведений — `null`.

В Librium есть прокси и подключение к локальным отладчикам приложения:

- **HTTP-прокси 127.0.0.1:8080**: HTTP/HTTPS и WebSocket клиентов, которые используют этот прокси. Для HTTPS/WSS клиент должен доверять CA Librium.
- **Подключить приложение → Окна / workers**: HTTP и WebSocket браузерной части Electron / Chromium через CDP.
- **Подключить приложение → Главный процесс / Node.js**: поддерживаемые сетевые события fetch / http / https через Node.js inspector. Обе отладочные сессии могут работать одновременно; для них не нужна настройка CA. Они не перенаправляют весь трафик процесса.

## Majestic Launcher

1. Запусти десктопную версию Librium.
2. Полностью закрой Majestic Launcher, включая значок в трее.
3. Нажми **Подключить приложение → Запустить Majestic Launcher**. Librium ищет установленный лаунчер в `%LOCALAPPDATA%\MajesticLauncher` и запускает его с двумя локальными отладочными портами: 9333 для окон и 9334 для главного процесса при стандартных настройках.
4. Проверь отдельные статусы двух источников, затем используй лаунчер обычным способом. Запросы появятся в общей истории. Фильтр **WebSocket** оставит только WS-соединения.
5. Для завершения нажми **Отключить захват**. История остаётся на диске, лаунчер продолжает работать. Обычный перезапуск лаунчера закрывает отладочные порты.

Установленная на машине разработчика версия лаунчера основана на Electron; при проверке через CDP удалось записать HTTP-запросы. Наличие WebSocket нельзя вывести только из использования Electron: в конкретном сценарии их может не быть. Автообновление / перезапуск лаунчера может сбросить отладочный порт: закрой его и повтори запуск через Librium.

Для другого совместимого приложения нажми **Выбрать приложение…**, укажи его `.exe` либо `package.json` проекта Electron, затем **Запустить выбранное**. Librium сохраняет выбранный путь в своём профиле и подключает оба источника. Для проекта требуется установленный `node_modules/electron/dist/electron.exe`. Проект запускается напрямую его Electron, без выполнения npm-скриптов. Приложение нужно полностью закрыть перед повторным запуском с захватом; Librium не завершает чужие процессы. Некоторые упакованные сборки Electron отключают отладчик — в таком случае статус покажет доступные источники и ошибку подключения остальных.

**Записывать главный процесс с начала запуска** включено по умолчанию. Librium запускает приложение с `--inspect-brk`, дожидается остановки перед первым кодом приложения, затем включает сетевые события и устанавливает наблюдатель WebSocket и продолжает выполнение. Так поддерживаемые запросы главного процесса, включая первый fetch и первые WS-сообщения, можно записать до обычного подключения окна. Статус источника Node.js показывает **с начала запуска** только при подтверждённой остановке. Если сборка проигнорировала режим, статус сообщает, что начало запуска не подтверждено. Запросы окон записываются после подключения источника Chromium; захват их самого первого запроса этим режимом не гарантируется.

Отдельный кратковременный процесс Librium снимает ожидание примерно через 12 секунд, если захват не подключился. Он работает и после завершения основного процесса Librium. Перед продолжением он проверяет PID приложения; если в ранней инициализации Electron ещё нет `process.pid`, проверяется владелец локального TCP-порта средствами Windows. Помощник не включает Debugger и не снимает произвольные точки останова работающего приложения. Ошибка подготовки помощника отменяет запуск с ожиданием; можно отключить режим начала запуска и повторить. Настройка флажка сохраняется в интерфейсе.

Для ручного запуска добавь параметры к команде приложения, затем в Librium нажми **Подключиться к порту**:

```text
--remote-debugging-port=9333 --remote-debugging-address=127.0.0.1
```

Выбери источник «Окна / workers» и порт 9333. Для главного процесса / Node.js запусти совместимое приложение с параметрами:

```text
--inspect=127.0.0.1:9334 --experimental-network-inspection
```

Затем выбери источник «Главный процесс / Node.js» и порт 9334. Параметры инспектора и доступность сетевых событий зависят от версии Node.js / Electron и настроек сборки приложения. Если один источник не подключился, другой продолжает работать, а статус показывает причину частичного подключения.

При ручном запуске с `--inspect-brk` оставь включённым флажок начала запуска и подключи источник Node.js до продолжения программы. Для уже работающего приложения можно отключить флажок и подключиться без ожидания остановки в начале. Отдельный помощник относится к запуску кнопкой Librium; ручной запуск с ожиданием требует подключения отладчика пользователем.

Подключение разрешено только к loopback. Порты доступны локальным программам до закрытия приложения. У каждого сохранённого запроса есть источник: «Прокси», «Окна», «Node.js» или «Адаптер». Отметка сохраняется после перезапуска.

## Morphius

Morphius — отдельное Electron-приложение. Закрой его окно, в Librium нажми **Подключить приложение → Выбрать приложение…**, укажи `package.json` из проекта Morphius и нажми **Запустить выбранное**. Оба источника подключаются автоматически. Путь сохраняется для следующих запусков Librium. Кнопка **Majestic Launcher** запускает официальный лаунчер отдельно.

Для ручного запуска текущей сборки Morphius из исходников выполни из каталога проекта:

```powershell
node node_modules/electron/cli.js --remote-debugging-port=9333 --remote-debugging-address=127.0.0.1 --inspect=127.0.0.1:9334 --experimental-network-inspection .
```

В Librium подключи «Окна / workers» к 9333, затем «Главный процесс / Node.js» к 9334. Источники работают одновременно. Обычный Morphius не требует прокси Librium; режим отладчика также работает без сертификата. Если включён явный режим Morphius `--librium-proxy`, один запрос может появиться и в прокси, и в Node.js: смотри отметку источника. Для нового WebSocket выполни действие, которое открывает соединение, после подключения источников. Запуск игры сам по себе не делает её отдельный процесс доступным этим отладчикам.

## Разбор сообщений

В верхней панели истории **Все источники** переключается на **Прокси**, **Окна**, **Node.js** или **Адаптер**. Фильтр применяется ко всему архиву до пагинации и сочетается с URL, типом трафика, статусом и дополнительными условиями. Это помогает разбирать запросы главного процесса Morphius отдельно от окон и записей прокси. Выбор сохраняется в сессии фильтров; метка **Источник** позволяет убрать только это условие. Старые сессии без указанного источника открываются с выбором всех источников.

В строке запроса и в инспекторе показывается **окно / поток**, если его передал сборщик. Нажми метку в инспекторе, чтобы оставить записи **только этого окна / потока в пределах подключения**. Разные цели с одинаковыми названиями и одинаковыми URL остаются раздельными. Условие видно отдельной кнопкой над историей, снимается нажатием и сохраняется в сессии фильтров. Оно работает по всему архиву до пагинации и сочетается с источником и остальными условиями.

Переименование окна не разрывает этот фильтр. Для следующих запросов Chromium обновляет известное название по уведомлениям инспектора и опросу списка целей примерно раз в секунду. Название у уже начатого HTTP-запроса или WS-рукопожатия сохраняется прежним. После отключения и нового подключения выдаётся новый контекст; сохранённый фильтр по предыдущему контексту продолжает находить его архивные записи. Это принадлежность к сеансу наблюдения, а не постоянный идентификатор процесса или пользователя.

Чтобы найти **все записи с нужным названием**, открой **Фильтры + → Окно / поток**: доступны сравнение, поиск подстроки и отрицательные условия. Регистр не учитывается, включая кириллицу. Отсутствующая метка не соответствует ни положительному, ни отрицательному условию по названию. В старой записи, где есть только название без контекста, нажатие метки применяет именно поиск по названию; это указано в подсказке кнопки.

Название хранится в `summary.capture_target`, принадлежность — в `summary.capture_context`; HTTP-заголовки не подменяют эти поля. Старые записи без этих сведений остаются без них. Для Node workers название включает номер и заголовок worker; для окон — заголовок цели Chromium. Название ограничено 256 символами Unicode и 1024 байтами UTF-8. Исходный регистр сохраняется в записи и JSONL. Запрос `/api/traffic-page?q=...` принимает необязательное точное условие `capture_context`; оно индексируется отдельно от названия, чувствительно к регистру и исключает записи без идентификатора. Адаптер может передать собственный уникальный идентификатор: 1–128 ASCII-символов из букв, цифр и `._:/-`. Неверный идентификатор отклоняется без записи.

Кнопка **Окна / потоки** в истории открывает список всех записанных контекстов, независимо от текущих фильтров. Для каждого показаны название и источник последней сохранённой записи, количество записей HTTP и WebSocket, время первой и последней записи. Порядок определяется ID записи, а не сравнением часов источника. WebSocket здесь включает попытки рукопожатия; число сообщений внутри соединения в этот счётчик не входит. Старые записи и трафик без идентификатора контекста показаны отдельным общим счётчиком, без угадывания принадлежности.

Поиск в списке проверяет **последнее название в снимке**, включая кириллицу. За один раз показываются 100 контекстов; «Старее» и «Назад» сохраняют границу снимка даже во время новой записи трафика. «Обновить» или новый поиск открывают свежий снимок. «Выбрать» добавляет точное условие контекста к остальным фильтрам истории и сохраняет его в текущей сессии. Если после выбора история пуста, проверь оставшиеся условия над ней.

Список читает только метаданные архива, без тел HTTP и сообщений WS. Для него используется отдельное чтение SQLite вместе с общим ограничением двух архивных читателей, поэтому длительный просмотр не держит мьютекс записи захвата. Интерфейс отправляет один запрос списка за раз и оставляет только последнее ожидающее действие; закрытие окна не позволяет позднему ответу изменить новое представление. API `GET /api/capture-contexts?q=...` требует обычный токен; JSON-параметры — `search` (до 256 символов / 1024 байт), `through` (граница снимка) и `before` (последняя запись предыдущей страницы). Ответ содержит `contexts`, `total`, `matched`, `without_context`, `through`, `older` и `next_before`. Идентификаторы контекстов остаются внутренними данными выбора, а в таблице показаны понятные названия.

Одинаковый URL может присутствовать у нескольких источников: например, запрос главного процесса может одновременно наблюдаться прокси и отладчиком Node.js. Выбор источника разделяет эти записи, но не объединяет их автоматически. Источник определяется сохранёнными метаданными захвата, а не произвольным HTTP-заголовком. Если под выбранные условия нет записей, интерфейс показывает «Ничего не найдено», сохраняя общий счётчик истории.

Выбери WebSocket-соединение: слева отправленные сообщения, справа полученные. Каждое сообщение содержит ID, локальное время с миллисекундами, тип, полный размер и признак частичного сохранения.

- **Авто / JSON** форматирует JSON, распознаёт распространённые пакеты Engine.IO / Socket.IO (события, namespace, ack, объявления бинарных вложений), пробует UTF-8 для бинарных сообщений.
- **MessagePack** разбирает бинарные сообщения только по явному выбору этого режима. Показывает массивы, карты, строки, числа и логические значения. Целые вне безопасного диапазона JavaScript показаны как `$integer` с точной десятичной строкой; бинарные значения — как `$binary` в Hex. Карты с нестроковыми или повторяющимися ключами сохраняют пары в `$map`; расширения, включая timestamp, показаны как `$extension` с типом и исходными байтами. Специальные float-значения отмечены `$float`, невалидный UTF-8 строки — `$stringBytes`. Эти метки относятся к представлению Librium, а не к исходному протоколу приложения.
- **Исходное** показывает текст без форматирования; бинарные сообщения представлены в Hex.
- **Hex** показывает сохранённые байты любого сообщения.

Поиск **Socket.IO: имя события** проверяет имя в первом элементе массива EVENT (`42[...]`) или текстового заголовка BINARY_EVENT (`451-[...]`). Например, `42/admin,17["inventory:update",{"item":"phone"}]` находится по `inventory`, но не по `phone`. Поиск подстроки учитывает регистр; пустой запрос выбирает все распознанные события. Namespace и ID подтверждения показываются в просмотре. Числовые имена сохраняют исходную запись числа без округления. Поиск проходит по всей записи соединения до разбиения на страницы, с учётом фильтров направления и типа; работает и после перезапуска. В API это `format:"socketio_event"` в параметрах поиска WS.

Кнопка **События Socket.IO** рядом с поиском открывает список до 100 самых частых событий по всей записи соединения. Для каждого показаны namespace, тип имени, полное число сообщений и разбиение на отправленные / полученные. Группы учитывают регистр и тип: число `17` и строка `"17"` различаются; числовые имена сохраняют исходную запись (`1` и `1.0` — разные группы). Итоги включают весь архив до ограничения таблицы; отдельно показаны исключённые сообщения и число сообщений вне списка. Пересчёт запускается вручную, захват продолжается.

**Найти точно** применяет имя вместе с типом и namespace, снимая фильтры направления и выбирая TEXT. Например, `chat` в `/admin` не совпадает с `chat:message` или `chat` в `/`. Точное условие видно над сообщениями; его можно снять кнопкой × или вводом новой подстроки. Фильтр направления можно добавить после выбора события. Список и поиск доступны после перезапуска и не меняют исходные сообщения. Строки в таблице ограничены 160 символами, копируется полное имя.

API списка: `GET /api/traffic/{id}/ws-socketio-events`, ответ `{id,total,matched,excluded,distinct,other,rows:[{namespace,kind,value,count,sent,received}]}`. Точный поиск: `POST /api/traffic/{id}/ws-search` с телом `{"format":"socketio_event","socketio_exact":{"namespace":"/admin","kind":"string","value":"chat"}}`. Значение `kind` — `string` или `number`, `value` всегда строка. Условие нельзя сочетать с подстрокой, полем JSON или другим форматом. Тело POST позволяет искать длинные имена без ограничения длины URL. Обоим запросам нужен `x-librium-token` текущего ядра.

В отдельном просмотре полного исходного Socket.IO-сообщения с ID подтверждения доступна кнопка **Найти событие / ACK** (формат **Авто / JSON**). Она ищет EVENT / BINARY_EVENT и ответ ACK / BINARY_ACK во всей записи этого WebSocket с тем же namespace и ID, в противоположных направлениях. Ссылки открывают исходное событие или ACK, включая сообщения за пределами текущей страницы. ID не переводится в число JavaScript и не округляется; ведущие нули не влияют на сопоставление. У события без ID нет запрошенного подтверждения, поэтому кнопка не показывается.

Пара отмечается найденной только при одном событии и одном ACK, записанном после него. Повторное использование ID, несколько ответов или обратный порядок дают статус «Неоднозначный ID» без автоматического выбора пары. Отсутствие ответа показано отдельно; поиск можно повторить после его записи. Выводится до 20 событий и 20 ACK, счётчики охватывают весь архив. Полные исходные данные сохраняются; неполные сообщения, отдельные бинарные вложения и выбранные диапазоны не используются как заголовки.

Интервал — разница времени записи текстовых заголовков события и ACK, а не измерение сетевой задержки или выполнения операции. Если часы идут назад, интервал не показывается. Для BINARY_EVENT / BINARY_ACK вложения не собираются и не проверяются: найденная пара заголовков не подтверждает полноту бинарного обмена. Правила ID / ACK сверены со [спецификацией Socket.IO](https://github.com/socketio/socket.io-protocol#acknowledgement).

API: `GET /api/traffic/{id}/ws/{message_id}/socketio-related` с `x-librium-token`. Для подходящего заголовка возвращаются `supported:true`, `status` (`matched` / `missing` / `ambiguous`), `ack_id` (строка), `namespace`, `events`, `acks`, `event_count`, `ack_count`, `inspected`, `pair` (ID другого сообщения либо null), `latency_ms` и `headers_only:true`. Элементы списков содержат ID сообщения, время, направление, имя события в `method` (null для ACK) и флаг `binary_header`. Неподходящий формат даёт `supported:false` с причиной; сообщение другого соединения или удалённая запись — HTTP 404.

Повреждённые и неполностью сохранённые сообщения, служебные пакеты, зарезервированные имена событий и отдельные бинарные вложения не совпадают с этим поиском. Поддерживается стандартный текстовый формат Socket.IO внутри Engine.IO WebSocket MESSAGE; пользовательские парсеры, MessagePack Socket.IO и HTTP polling требуют другого разбора. Заголовок BINARY_EVENT распознаётся отдельно: наличие и целостность его вложений этим не подтверждаются. Формат заголовка и допустимые имена сверены с [официальным Socket.IO parser](https://github.com/socketio/socket.io/blob/main/packages/socket.io-parser/lib/index.ts).

Распознавание протокола эвристическое: например, строка `2` может означать Engine.IO PING, а может быть числом прикладного протокола. Исходные байты доступны независимо от выбранного представления. Бинарные вложения Socket.IO показываются отдельными сообщениями; автоматическая сборка вложений не выполняется.

MessagePack автоматически не угадывается. Поддерживается одно значение на сообщение; дополнительные байты и повреждённый формат дают явную ошибку, а не частичный результат. Обрезанное сообщение не разбирается даже при корректном начале. Разбор ограничен 64 КиБ, 64 уровнями вложенности и 10000 значениями. Для собственного протокола с заголовком перед MessagePack укажи его длину в поле «Разбор с байта» отдельного инспектора сообщения; исходное представление / Hex сохраняют весь пакет. Заголовок автоматически не отбрасывается.

Если по всем условиям во всей записи нет совпадений, поиск возвращает пустую страницу после подсчёта и не выполняет повторный полный разбор сообщений для выборки страницы. Счётчики, состояние соединения, ошибка и сведения о закрытии берутся из того же снимка. Результат не кешируется как постоянный: следующий запрос видит новые подходящие сообщения, а просмотр старого снимка остаётся согласованным. Это сокращает лишнюю работу при подборе значений и полей в больших записях; запросы с совпадениями сохраняют обычную пагинацию.

Поле **Поиск по всей истории сообщений WS** ищет среди всех сохранённых сообщений выбранного соединения, включая старые страницы. В режиме **Поиск: текст** используется сохранённый текст. Регистр кириллицы и латиницы не учитывается. Режим **Поиск: MessagePack** разбирает бинарные сообщения и ищет по их декодированным полям и значениям. Текстовые сообщения в этом режиме ищутся обычным способом. В режиме MessagePack повреждённые и обрезанные бинарные сообщения не получают совпадений по непроверенному префиксу. Выбор поиска MessagePack также переключает представление сообщений на MessagePack; исходные байты остаются доступны в Hex.

Режим **Поиск: UTF-8** ищет по сохранённому тексту и декодированным байтам бинарных сообщений, в том числе с читаемым JSON. Он работает и со старой историей, где у бинарного сообщения поле `text` пустое. Невалидный UTF-8 не заменяется символами `�` и не даёт текстовых совпадений. Если сообщение помечено обрезанным и только последний многобайтный символ не закончен, доступен корректный текстовый префикс до этого символа. Просмотр «Авто / JSON» показывает тот же префикс; исходные байты, включая незавершённый символ, сохраняются в Hex и JSONL. Строка сообщения указывает фактический размер сохранённых байтов, если оно обрезано.

Фильтр типа ограничивает поиск TEXT / BINARY / служебными сообщениями. Рядом можно выбрать **Оба направления**, **Отправлено** (клиент → сервер) или **Получено** (сервер → клиент). Направление применяется ко всему архиву до пагинации и сочетается с типом и форматом поиска. Поэтому старую отправку можно найти даже среди сотен более новых ответов сервера. Панели WS называются «Отправлено» и «Получено»; скрытая фильтром панель получает пояснение. Если в общей странице нет сообщений одного направления, это отмечается отдельно от отсутствия сообщений во всём соединении.

Кнопка **Раньше** загружает предыдущие 100 подходящих сообщений, **К новым** возвращает последнюю страницу. При смене направления просмотр возвращается к последней странице результатов. Декодирование выполняется при поиске и работает с ранее записанной историей, без изменения сообщений. Обычный поиск над панелями подсвечивает текст текущего представления. В API `GET /api/traffic/{id}/ws?q=...` поле `direction` принимает `sent`, `received` или пустую строку для обоих направлений; отсутствие поля сохраняет прежнее поведение.

## Экспорт WebSocket

Кнопка **Экспорт JSONL** сохраняет все записанные сообщения выбранного соединения, независимо от поиска, направления, типа сообщения и текущей страницы. Выбери место для файла `.jsonl`. Сообщения идут в порядке архивных ID: сохраняются `id`, `time`, `direction`, `kind`, исходные `text` / `base64`, полный наблюдённый `size` и `truncated`. Экспорт не восстанавливает байты за пределами сохранённого предпросмотра.

Каждая строка — отдельный JSON-объект. Первая запись имеет `type: "session"`: версия формата, данные обмена с источником и заголовками, состояние соединения на начало экспорта, число сообщений `total` и граница снимка `through`. Затем следуют записи `type: "message"`. Последняя запись `type: "end"` содержит итоговое число `messages` и ту же границу снимка. Новые сообщения живого соединения не попадают в уже начатый экспорт; повторная выгрузка включает их. Итоговый счётчик должен совпадать с `total` первой записи.

В настольной версии данные записываются порциями во временный файл рядом с выбранным. Выбранный файл заменяется после проверки полного количества сообщений; отмена или ошибка не заменяет существующий файл. Закрытие Librium отменяет выполняемую выгрузку и дожидается очистки временного файла. Браузерная версия использует File System Access API, если браузер предоставляет сохранение файлов; иначе кнопка недоступна. Это локальная выгрузка файла.

Для собственного инструмента доступен авторизованный `GET /api/traffic/{id}/ws-export?after=0`. Первая страница возвращает `session`, сообщения, `through`, `next` и `more`. Продолжай с `after=next&through=through` до `more: false`; на последующих страницах `session` равен `null`. Фиксированная граница и проверка итогового числа защищают выгрузку от смещения при поступлении новых сообщений или очистке истории. Без заголовка `x-librium-token` API недоступен.

## Границы захвата CDP

Настольная сборка проверяет `desktop_api` и необходимые возможности Rust-ядра до загрузки истории. Если на порту 3000 осталось ядро от другой сборки, Librium показывает сообщение о несовместимости и не применяет новые фильтры к старому API. Закрой ранее запущенный Librium, включая отдельно запущенное ядро в терминале, затем открой обновлённую сборку. Настольное приложение не завершает чужой процесс ядра. При неудачной проверке запросы приложения блокируются; при выходе не отправляются команды сброса данных несовместимому ядру.

В общем списке фильтр **Ожидание** выбирает записи без HTTP-кода и без пояснения ошибки. Фильтр **Сбой / прервано** выбирает записи с технической ошибкой или отметкой о завершении наблюдения. У завершённой попытки без HTTP-кода показано **Нет ответа**; причина доступна при наведении и в деталях. Если код уже получен, он сохраняется и получает отметку `!`, например `202 !`, когда наблюдение было прервано позже. Сам по себе ответ 4xx / 5xx без технической ошибки не относится к этому фильтру: для него доступны фильтры по классу HTTP-кода. Состояние фильтра сохраняется вместе с выбранной сессией фильтров.

Попытка WebSocket, для которой ещё не получен ответ на рукопожатие, тоже сохраняется при отключении, потере отладочного соединения или закрытии окна / worker. У такой записи нет подтверждённого статуса `101` и нет открытой сессии сообщений. Фильтр WebSocket включает её как попытку соединения. Если замечен только адрес, отправка и заголовки помечаются неподтверждёнными. Причина завершения наблюдения не означает, что приложение не смогло подключиться: после отключения Librium рукопожатие может успешно завершиться.

При отключении захвата, потере отладочного соединения или закрытии окна / worker незавершённые HTTP-запросы сохраняются в архиве. Известные заголовки и доступное тело запроса остаются в записи; недоступное тело не считается пустым. Ответ помечается неполным, причина указывает на завершение наблюдения. Эта отметка не доказывает сбой запроса в приложении: после отключения Librium приложение может продолжить запрос и получить ответ. Показанная длительность — время наблюдения до отключения. При обычном отключении Librium сначала получает снимки тел Node.js и затем снимает наблюдатель; при внезапной потере соединения получить новые снимки уже невозможно.

Захват начинается после подключения отладчика. Для WebSocket, открытого раньше, нужно переподключение в клиенте. Новые окна и дочерние workers подключаются автоматически. Источник Node.js отдельно записывает поддерживаемые запросы главного процесса. Electron net, нативные модули, TCP/UDP и отдельный игровой процесс могут быть недоступны обоим отладчикам. HTTP/3 и TLS внутри нативного кода этим режимом не декодируются.

Для тела HTTP и каждого WS-сообщения сохраняется до 64 КиБ, полный размер WS-сообщения учитывается отдельно. HTTP-тела источника «Окна» уже декодированы браузером; исходные заголовки сохраняются, служебный заголовок `x-librium-body-decoded` предотвращает повторную распаковку в интерфейсе. Если CDP не отдаёт тело (например, превышен буфер 1 МиБ на ресурс), в заголовках появляется `x-librium-capture-note`. Размер HTTP источника «Окна» отражает доступное декодированное тело, а не число байтов TLS на проводе.

Для запросов источника «Окна» используются бинарные `postDataEntries`, если они доступны. При отдельном получении тела через `Network.getRequestPostData` учитывается флаг `base64Encoded`: строка base64 декодируется только при этом флаге. Это сохраняет исходные байты бинарных тел и Blob, включая невалидный UTF-8. Если среди элементов тела есть пропуск, например недоступный файл, сохраняется только непрерывный префикс до пропуска и ставится отметка неполноты. Размер при пропуске может быть неизвестен; лимит предпросмотра — 64 КиБ.

Источник Node.js сохраняет исходное тело ответа, включая gzip / deflate: Pretty распаковывает его, Hex показывает сохранённые исходные байты. Инспектор ограничивается буфером 8 МиБ суммарно и 1 МиБ на ресурс; в историю всё равно записывается только предпросмотр 64 КиБ. Если известен Content-Length исходного ответа, сохраняется полный размер; если буфер обрезал ответ без известного полного размера, интерфейс прямо сообщает об этом.

Node.js inspector не всегда отдаёт тело POST: может сообщить `Unable to serialize binary request body` даже для текстового JSON, представленного внутри Node.js байтами. Для fetch / совместимого Undici временный наблюдатель дополнительно записывает `undici:request:bodyChunkSent` и `bodySent`. Он получает уже переданные транспорту байты и не читает исходный поток приложения. Запись связывается с запросом по ID инспектора на объекте Undici, без сопоставления по URL: параллельные запросы на один адрес остаются раздельными. Поддерживаются JSON / текст, бинарные данные и потоковые тела; сохраняются первые 64 КиБ и наблюдённый размер.

Снимок тела берётся при сохранении ответа или ошибки запроса. Если при создании снимка отправка ещё не закончилась, например при раннем ответе сервера, показан только наблюдённый префикс, с отметкой неполного тела и неизвестного полного размера. После обрыва сохраняется доступный префикс с пояснением. Отсутствие диагностических байтов само по себе не подтверждает пустое тело, например у неизвестного пустого потока или старой версии Undici. Совместимость использует внутренний ID Node.js; если он недоступен, остаётся стандартный метод инспектора. Для прямых http / https, других транспортов и несовместимых версий тело по-прежнему может быть недоступно. Такое тело помечается явно; ответ сохраняется отдельно. Неизвестное тело не показывается подтверждённо пустым и не получает ложную ошибку оборванного соединения после перезапуска Librium.

Если отправка тела уже подтверждена, последующий сбой получения ответа не меняет полноту тела запроса. Ошибка остаётся у обмена и ответа: это позволяет отличить прерванную загрузку от сбоя после полной отправки.

Предпросмотры исходящих тел используют отдельный пул 8 МиБ и до 2000 ожидающих запросов. После получения снимка или отключения наблюдения память освобождается. При превышении лимита новые данные тела могут быть пропущены с пояснением; само приложение продолжает отправку.

В используемой версии Node.js inspector доступны только рукопожатие и состояние WebSocket. Для встроенного WebSocket в совместимом Node.js Librium дополнительно устанавливает временный наблюдатель через Runtime binding и диагностический канал Undici. Он оборачивает WebSocket.prototype.send и при необходимости send отдельного экземпляра, добавляет обработчики message / close и записывает текст, ArrayBuffer / typed arrays и Blob. Значение binaryType не меняется; ошибки и результат send сохраняются. Это сообщения приложения после сборки и распаковки, а не сырые кадры с флагами, ping / pong и фрагментацией. Заголовки запроса рукопожатия этим путём недоступны. Если версия Undici не предоставляет экземпляр WebSocket, остаются только данные инспектора с пояснением. HTTP/2 WebSocket и нативные сокеты этим наблюдателем не поддерживаются.

Для клиентских и новых серверных соединений отдельно установленного пакета **ws** есть дополнительный наблюдатель (проверено на ws 8.21.3 / Electron 44.2). Он временно оборачивает события класса и методы Sender конкретного соединения. Исходящие параметры читаются после нормализации библиотекой: пользовательские геттеры не вызываются повторно, а callbacks и ошибки сохраняются. Фрагменты исходящего сообщения собираются в один текстовый или бинарный пакет, входящие данные записываются после сборки и распаковки библиотекой. Поддерживаются стандартные Buffer, ArrayBuffer / typed arrays, Blob и входящий режим binaryType=fragments, а также PING / PONG. Для незавершённого исходящего сообщения при закрытии сохраняется пояснение. Неподдерживаемый тип данных пропускается с предупреждением.

Для уже загруженного ws читается кэш модулей приложения; последующая обычная загрузка CommonJS / ESM отслеживается через временный module.registerHooks. К исходнику загружаемого CJS-модуля ws в памяти добавляется регистрация класса наблюдателю. При отключении хук удаляется, а методы восстанавливаются, если приложение само их не заменило. Это не распространяется на ws, встроенный сборщиком в общий bundle, уже принятые до подключения наблюдателя серверные сокеты ws, переименованные или нестандартные сборки библиотеки. Если runtime не поддерживает синхронные хуки, доступны уже загруженные модули; после поздней загрузки потребуется переподключить источник. Если наблюдение началось на уже открытом соединении с входящего сообщения, запись явно помечается как начатая после рукопожатия.

При отключении Librium снимает наблюдатель и восстанавливает методы, если приложение само не успело их заменить. Подключение обновляет аренду каждую секунду; при потере отладчика обработчики снимаются примерно через 5–6 секунд. Отправка самим приложением продолжается. Для каждой Blob-очереди лимит — 1 МиБ, суммарно — 8 МиБ; для незавершённых исходящих сообщений ws отдельно ограничен суммарный предпросмотр 8 МиБ; количество ожидающих сообщений также ограничено, включая пустые. При переполнении наблюдатель прекращает запись и сообщает об этом. Для сообщений сохраняются первые 64 КиБ и полный размер. Новое соединение нужно открыть после подключения источника.

Источник **Главный процесс / Node.js** также автоматически подключает `worker_threads`, включая вложенные workers. В архиве они сохраняют источник «Node.js», а заголовок `x-librium-target` указывает отдельный worker. Счётчики источника включают их запросы и сообщения. Проверены workers из eval, CommonJS и ESM-файлов, встроенный WebSocket и поздняя загрузка `ws` в Node.js 25 и Electron 44. Для HTTP в этих проверках включён `--experimental-network-inspection`; кнопка запуска Librium уже добавляет его. В других сборках доступность зависит от инспектора; при невозможности подключения статус сообщает об ограничении.

Для нового worker наблюдатель устанавливается на подтверждённой стартовой остановке до основного кода. Побочные действия импортируемых ESM-зависимостей до этой остановки могут не попасть в запись. Если остановка не подтверждена, worker продолжает выполнение, а статус предупреждает о возможном пропуске ранних запросов. К уже работающим workers наблюдатель подключается без стартовой остановки; прошлые запросы и сообщения не восстанавливаются.

Одновременно наблюдаются до 32 Node workers. Для каждого лимит активных записей HTTP / WS — 64, очередей WebSocket, фрагментов ws и тел HTTP — по 1 МиБ; очередь событий 8 МиБ общая с главным процессом. Достижение лимита ограничивает наблюдение, а приложение продолжает работать. Новые workers сверх лимита освобождаются от ожидания отладчика. Локальный канал инспектора в главном процессе снимает собственные стартовые остановки примерно через 5 секунд при потере связи или незавершённой установке наблюдателя. Он закрывает свои worker-сессии после истечения аренды; это позволяет потокам завершаться штатно. Нормальное отключение также освобождает worker, даже если установка наблюдателя ещё не закончена.

Очередь событий ограничена 8 МиБ; при переполнении или ошибке сохранения захват останавливается с сообщением в статусе. Данные продолжают передаваться самим приложением. После отключения или перезапуска незакрытые сессии помечаются завершёнными.

## Собственная схема полей

Открой TEXT / BINARY сообщение и нажми **Поля протокола**. Добавь имя поля, смещение от начала исходного сообщения и тип. Например: `command`, смещение `0`, тип `uint16`, порядок `LE`; затем `request_id`, смещение `2`, тип `uint64`. Смещения и длины принимают десятичные числа и Hex (`0x0c`). Каждое поле можно изменить, удалить, полностью скопировать или открыть его доступные байты в Hex. Кнопка «Копировать таблицу» копирует значения вместе с типами, смещениями и статусами; управляющие символы в именах / значениях экранированы как JSON.

Поддерживаются `uint8/16/32/64`, `int8/16/32/64`, `float32/64`, `bytes` (Hex) и `utf8` фиксированной длины. Для многобайтных чисел выбирается LE (младший байт первым) или BE (старший первым). Целые 64 бит показаны точными десятичными строками; у float сохраняются `-0`, `NaN` и бесконечности. UTF-8 проверяется строго, включая границы заданного поля; некорректные байты не заменяются символами, BOM не удаляется. Автоматический поиск конца строки и чтение длины из другого поля не выполняются.

Схема — твоя гипотеза о формате, а не автоматическое распознавание протокола. Она всегда читает исходные байты, независимо от выбранного смещения разбора, диапазона или распаковки. Сообщения и экспорт не меняются. Если поле выходит за полный размер сообщения, показано «За пределами сообщения». Если поле помещается в полный размер, но его хвост не сохранён, показано «Байты не сохранены». Нули и значения по неполному префиксу не подставляются. Для невалидного UTF-8 поле отмечено отдельно; исходные байты остаются доступны в Hex.

**Сохранить схему** сохраняет только имена полей, типы, смещения, длины и порядок байтов на этом устройстве. Значения сообщений не входят в настройки. При следующем открытии сообщения схема применяется заново. Можно хранить до 20 схем, по 64 поля в каждой; имена — до 64 символов. Начало поля — байт 0–65535, длина `bytes` / `utf8` — 1–65536 байт, суммарная длина полей — до 256 КиБ. Перекрывающиеся поля допустимы. В таблице видны первые 160 символов, копируется полное значение; слишком большую таблицу можно копировать по отдельным полям. Несохранённый черновик держится до закрытия приложения; «Удалить схему» удаляет сохранённые настройки, оставляя текущий черновик. Повреждённые или неподдерживаемые сохранённые настройки не перезаписываются автоматически.

Кнопка **Найти точно** у успешно прочитанного поля ищет это значение по всей записи исходного соединения, до разбивки на страницы. Учитываются смещение, тип, длина и порядок байтов. Поиск выбирает TEXT / BINARY в обоих направлениях; направление и тип можно затем сузить. Точное условие видно над сообщениями. × снимает его, а ввод текста возвращает обычный текстовый поиск. Переход к другому соединению также снимает условие. Открытие найденного сообщения сразу выделяет байты поля в Hex.

Целые ищутся без округления, UTF-8 — с учётом регистра и точного байтового представления; `bytes` — как фиксированная последовательность по заданному смещению. `+0` и `-0` у float различаются. Запрос `NaN` находит любые NaN выбранного типа и порядка байтов, независимо от битовой формы NaN. Конечные float приводятся к объявленному типу (`float32` / `float64`) и затем сравниваются побайтово. Частично сохранённый пакет может совпасть, если все байты выбранного поля сохранены; неполный префикс поля, неверный размер и служебные кадры не совпадают. Исходные сообщения не меняются.

API точного поиска: `POST /api/traffic/{id}/ws-search`, заголовок `x-librium-token`, пример тела: `{"format":"protocol_field","field_exact":{"type":"uint64","offset":2,"endian":"le","value":"18446744073709551615"}}`. Для `bytes` / `utf8` обязателен `length`; для числовых типов длина определяется типом и не передаётся. `value` всегда строка; Hex — пары байтов через один пробел. Такое условие нельзя сочетать с подстрокой, JSON Pointer или другим точным условием. Используется POST, поэтому длинные значения не попадают в URL. Совпавшие сообщения в ответе получают `match_offset` и `match_length` для выделения; отдельное чтение сообщения и JSONL-экспорт сохраняют исходные данные без этих аннотаций. Поиск работает по сохранённому архиву после перезапуска.

Для сравнения двух сообщений сначала выбери **Выбрать образец** в отдельном окне первого пакета. Открой второй пакет, затем **Поля протокола** → **Сравнить поля с образцом**. Одна схема читается из исходных байтов A (образца) и B (текущего сообщения). Таблица показывает оба значения и результат сравнения. По умолчанию скрыты поля без изменений и поля вне границ обоих сообщений; отключи «Только отличия и неполные данные», чтобы увидеть всю схему. Невалидный UTF-8 остаётся в списке. Для редактирования полей нажми **Вернуться к схеме**. Образец хранится в памяти до сброса или закрытия приложения; можно сравнивать сообщения из разных соединений. Для полей нужен образец TEXT / BINARY.

«Значение изменилось» означает два успешно прочитанных разных значения. Если значения те же, но байты различаются (например, разные битовые формы NaN), это отмечено отдельно. `-0` и `+0` различаются. «Сравнение неполное» не считает несохранённый хвост совпадением, даже если доступные байты одинаковы. Выход поля за полный размер сообщения отмечен отдельно от отсутствующего сохранённого хвоста. При невалидном UTF-8 сравниваются доступные полные байты без догадок о тексте.

**Копировать A** копирует полное значение образца; обычная кнопка копирования, переход в Hex, поиск и сводка значений относятся к текущему сообщению B. **Копировать таблицу** включает все поля схемы, даже скрытые фильтром, с обоими полными значениями, типами, смещениями и статусами. Экспорт / сохранение схемы по-прежнему содержит только настройки полей. Изменение или сброс образца сбрасывает сравнение полей; при открытии другого сообщения оно начинается в обычном режиме. Исходные данные, фильтры просмотра и JSONL-экспорт не изменяются. Выбранное смещение разбора и распаковка не меняют байты образца и текущего пакета для сравнения полей.

Кнопка **Значения** у поля открывает частотную сводку по всей записи соединения, независимо от страницы, поисковой строки и фильтров направления / типа. Она доступна и тогда, когда текущее сообщение слишком короткое для поля: в архиве могут быть другие подходящие пакеты. Для каждого значения видны число сообщений и разбиение на отправленные / полученные; **Найти точно** открывает совпадения в исходном соединении с теми же типом, смещением и порядком байтов. В список попадает до 100 самых частых значений, но итоги и число разных значений считаются до этого ограничения. Отдельно показаны исключённые сообщения и число сообщений вне списка.

Используются только полностью сохранённые байты поля. Остальная часть сообщения может быть сохранена частично. Неполное поле, неверные метаданные, служебный кадр и невалидный UTF-8 не входят в сводку. UTF-8 учитывает регистр и отображается как JSON-строка, чтобы были видны управляющие символы; копируется полное исходное значение без кавычек. Целые 64 бит читаются без округления. Для float битовые формы NaN объединены в одну группу, а `+0` и `-0` различаются — как в точном поиске. Сводка обновляется вручную; захват продолжается, поэтому последующий поиск может найти уже добавленные сообщения. Значения не сохраняются в настройках схемы.

API сводки: `POST /api/traffic/{id}/ws-field-values` с `x-librium-token` и описанием поля, например `{"type":"uint16","offset":0,"endian":"le"}`. Для `bytes` / `utf8` обязателен `length`. Передавать имя или искомое значение не нужно; неизвестные свойства отклоняются. Ответ: `{id,field,total,matched,excluded,distinct,other,rows:[{base64,count,sent,received}]}`. `base64` содержит байты значения поля для разбора по `field`, а не сообщение. Для группы NaN возвращается каноническая битовая форма NaN. Исходные сообщения и экспорт не меняются. Соединение вне истории — HTTP 404; чтение выполняется по согласованному снимку сохранённой записи и работает после перезапуска.

**Копировать схему** переносит текущий черновик в JSON, без значений открытого сообщения. Его можно хранить вместе с проектом или передать другому пользователю Librium. Кнопка **Импорт схемы** принимает этот JSON, проверяет версию и все поля, затем заменяет текущий черновик и пересчитывает значения на открытом сообщении. Сохранённые схемы не меняются до отдельного нажатия **Сохранить схему**. Если имя уже существует, сохранение под этим именем обновит его; для отдельной схемы измени имя перед сохранением. Ошибка импорта оставляет прежние поля и настройки на месте. Закрытие родительского окна во время ввода отменяет импорт и очищает вставленный JSON.

Формат переноса одной схемы: `{"version":1,"schema":{"name":"Мой протокол","fields":[{"name":"command","offset":0,"type":"uint16","endian":"le"}]}}`. Для `bytes` / `utf8` нужно добавить `length`; у чисел длина определяется типом. В JSON принимаются только поля определения схемы: код, значения трафика, неизвестные свойства и неподдерживаемые версии отклоняются. Максимум — 65536 символов JSON, остальные ограничения полей те же. Экспорт нормализует смещения в числа. Незавершённую правку существующего поля нужно применить или отменить перед копированием либо сохранением схемы.

В настольном приложении схемы хранятся в его локальном профиле, в браузере — в хранилище текущего сайта. Очистка истории запросов не удаляет настройки схем. Поля протокола недоступны для служебных WS-кадров.

## Подключение собственного адаптера

Локальный API `POST /api/capture` принимает JSON-события. Нужен заголовок `x-librium-token` текущего ядра; renderer Electron не получает прямого доступа к этому API. Адаптер работает с разрешения пользователя на той же машине.

1. `{"event":"exchange","exchange":{...},"websocket":true}` создаёт запись и возвращает `{"id":123}`. `exchange` имеет ту же структуру, что `GET /api/traffic/{id}`: `summary`, `request`, `response`. Ядро назначает ID независимо от переданного значения. Необязательное поле `summary.source` принимает `cdp_node` / `cdp_chromium`; остальные события этого API сохраняются как `external`, а обычный прокси использует `proxy`. Для WS нужен подтверждённый статус 101; отказ рукопожатия сохраняется с `websocket:false`.
2. `{"event":"message","id":123,"message":{...}}` добавляет WS-сообщение. Поля: `time` (Unix-миллисекунды), `direction` (`sent` / `received`), `kind` (`TEXT`, `BINARY`, `PING`, `PONG`, `CLOSE`, `CONTINUATION`), `text`, `base64`, `size`, `truncated`. `size` — полный размер, `base64` — первые 65536 байтов, `truncated` должен соответствовать размеру.
3. `{"event":"end","id":123,"error":null}` завершает сессию. Если источник сообщил закрытие WebSocket, можно добавить `"close":{"code":1000,"reason":"Готово"}`. Код — целое число 0–65535, причина — строка до 4096 байтов UTF-8. Для непосредственно наблюдаемого CLOSE-кадра доступно необязательное направление `direction` (`sent` / `received`). При завершении наблюдения без события закрытия передавай `close:null` или опусти поле.

Сообщения принимаются только для открытой сессии внешнего адаптера. Очистка истории удаляет и её сессии; дальнейшие события удалённых сессий отклоняются. Операции с хранилищем и ошибки возвращаются адаптеру явно.
