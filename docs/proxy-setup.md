# Librium: настройка прокси в Windows 10 и как это устроено

[← Назад к индексу](../README.ru.md) · Связано: [Архитектура](architecture.md), [Сеть](network.md), [Реестр Windows](basics/windows-registry.md)

Дополнение к [архитектуре](architecture.md) и [сети](network.md). Здесь про то, как приложения
узнают, что им надо ходить через 127.0.0.1:8080, где эти настройки лежат,
кто их читает, а кто игнорирует, и как всё проверить.

---

## 1. Главная идея

В Windows нет одного «системного прокси», которому подчиняются все программы.
Есть несколько независимых механизмов, и каждая программа сама решает,
какой из них уважать:

| Механизм                    | Кто хранит                          | Кто читает                                   |
|-----------------------------|-------------------------------------|----------------------------------------------|
| WinINET (настройки Internet)| реестр HKCU, «Параметры > Прокси»   | Chrome, Edge, Explorer, большинство GUI-программ |
| WinHTTP                     | реестр HKLM, `netsh winhttp`        | службы Windows, Windows Update, часть .NET   |
| Переменные окружения        | `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` | curl, git, pip, Python requests, Go, Rust reqwest, Node (частично) |
| Собственные настройки       | конфиг программы                    | Firefox, Java, Telegram, Docker, многие CLI  |
| Аргументы запуска           | командная строка                    | `chrome.exe --proxy-server=...`              |

Отсюда правило: если трафик программы не появился в прокси, сначала
выясняем, какой из механизмов она читает.

## 2. WinINET: то, что называют «системным прокси»

Это настройки из «Параметры > Сеть и Интернет > Прокси-сервер»
(или старое окно «Свойства браузера > Подключения > Настройка сети»).
Физически лежат в реестре текущего пользователя (что такое реестр и чем
HKCU отличается от HKLM, см. [Реестр Windows](basics/windows-registry.md)):

    HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings

Ключевые значения:

| Значение          | Тип       | Смысл                                                    |
|-------------------|-----------|----------------------------------------------------------|
| `ProxyEnable`     | DWORD     | 1 = прокси включён, 0 = выключен                         |
| `ProxyServer`     | REG_SZ    | `127.0.0.1:8080` или по протоколам `http=127.0.0.1:8080;https=127.0.0.1:8080` |
| `ProxyOverride`   | REG_SZ    | список исключений через `;`, например `*.local;192.168.*;<local>` |
| `AutoConfigURL`   | REG_SZ    | адрес PAC-файла, см. раздел 4                            |
| `AutoDetect`      | DWORD     | 1 = искать прокси через WPAD (по умолчанию включено)     |

Примеры.

**Включить прокси через реестр (PowerShell):**

    $k = 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings'
    Set-ItemProperty $k ProxyEnable 1
    Set-ItemProperty $k ProxyServer '127.0.0.1:8080'
    Set-ItemProperty $k ProxyOverride '<local>'

**Выключить:**

    Set-ItemProperty $k ProxyEnable 0

**Посмотреть текущее:**

    Get-ItemProperty $k | Select ProxyEnable, ProxyServer, ProxyOverride, AutoConfigURL

Важный нюанс: после записи в реестр нужно уведомить систему, иначе
уже запущенные программы не заметят изменение. Окно «Параметры» делает это
само, а из скрипта надо вызвать WinAPI:

    InternetSetOption(NULL, INTERNET_OPTION_SETTINGS_CHANGED, NULL, 0)
    InternetSetOption(NULL, INTERNET_OPTION_REFRESH, NULL, 0)

Именно так делают Burp и Caido, когда предлагают «настроить прокси
автоматически». В Rust это вызов через крейт `windows` или `winapi`,
функция из `wininet.dll`. Если Librium захочет кнопку «включить системный
прокси», нужно записать три значения выше и дёрнуть эти два вызова.

Исключения (`ProxyOverride`):

- `<local>` означает «адреса без точки», то есть `localhost`, `myserver`,
  но не `127.0.0.1`.
- Явный `127.0.0.1;localhost` нужен, если хочется не проксировать
  локальные сервисы.
- `<-loopback>` наоборот заставляет проксировать localhost. Полезно, когда
  тестируемое приложение работает на локальной машине: без этого Chrome
  и Edge всегда ходят на localhost напрямую, мимо прокси.

## 3. WinHTTP: прокси для служб

Отдельный стек, которым пользуются службы без интерактивного пользователя:
Windows Update, часть PowerShell-командлетов, некоторые .NET-приложения.
Настройки лежат в [HKLM](basics/windows-registry.md#3-hkcu-и-hklm-в-чём-разница),
общей для всех пользователей ветке, и меняются так:

    netsh winhttp show proxy
    netsh winhttp set proxy 127.0.0.1:8080 "<local>"
    netsh winhttp import proxy source=ie      # скопировать из WinINET
    netsh winhttp reset proxy

Для тестирования браузерных приложений это обычно не нужно. Понадобится,
если захочется посмотреть трафик какой-нибудь службы.

## 4. PAC и WPAD: прокси по правилам

**PAC** (Proxy Auto-Config) это файл на JavaScript с одной функцией.
Браузер вызывает её для каждого URL и получает решение:

    function FindProxyForURL(url, host) {
        if (shExpMatch(host, "*.target-app.com")) {
            return "PROXY 127.0.0.1:8080";
        }
        if (isInNet(host, "192.0.2.10", "192.0.2.11")) {
            return "DIRECT";
        }
        return "DIRECT";
    }

Возвращаемые значения: `DIRECT`, `PROXY host:port`, `SOCKS5 host:port`,
можно перечислить через `;` как запасные варианты.

Адрес PAC задаётся в `AutoConfigURL`. На Windows 10 это должен быть
http-адрес, `file://` современные браузеры игнорируют. Проще всего
раздать PAC своим же прокси: Librium может отдавать его по адресу
вроде `http://127.0.0.1:8080/librium.pac`. Так удобно проксировать
только цель тестирования, а остальной трафик пускать напрямую.

**WPAD** (Web Proxy Auto-Discovery) это автоматический поиск PAC-файла:
система запрашивает у DHCP опцию 252 и делает DNS-запрос `wpad.<домен>`.
Включён по умолчанию (`AutoDetect = 1`). В домашней сети обычно ничего
не находит. Для безопасности это известный вектор: кто ответит на `wpad`,
тот и станет прокси для всей сети. Для Librium его лучше отключить, чтобы
не мешал.

## 5. Как настраиваются конкретные программы

### Chrome, Edge, Chromium-приложения (Electron)

По умолчанию читают WinINET. Способы направить в Librium:

- Системный прокси из раздела 2.
- Ключ запуска, действует только на этот экземпляр:

      chrome.exe --proxy-server="127.0.0.1:8080" --user-data-dir="D:\tmp\chrome-librium"

  Отдельный `--user-data-dir` даёт чистый профиль, где можно спокойно
  установить CA Librium и не смешивать с рабочим.
- Ключ `--proxy-bypass-list="<-loopback>"`, чтобы проксировать localhost.
- Ключ `--ignore-certificate-errors` временно, пока CA не установлен.
- Расширения вроде Proxy SwitchyOmega для переключения профилей.

Chromium сам делает DNS через прокси (шлёт CONNECT с именем хоста),
и при настроенном HTTP-прокси не использует QUIC. Оба факта на руку прокси.

### Firefox

Игнорирует WinINET по умолчанию. Настройки: «Параметры > Основные >
Параметры сети». Там выбор: «Использовать системные настройки прокси»,
«Ручная настройка», «Автоматическая (PAC)». Расширение FoxyProxy позволяет
переключать профили по клику.

У Firefox своё хранилище сертификатов. Чтобы он доверял CA Librium, либо
импортировать в «Параметры > Приватность и защита > Сертификаты», либо
включить `security.enterprise_roots.enabled = true` в about:config, тогда
Firefox начнёт доверять хранилищу Windows.

Отдельно стоит выставить `network.proxy.allow_hijacking_localhost = true`,
иначе localhost идёт мимо прокси.

### curl, git, pip, wget, Go, Rust (reqwest), Python (requests)

Читают переменные окружения:

    $env:HTTP_PROXY  = 'http://127.0.0.1:8080'
    $env:HTTPS_PROXY = 'http://127.0.0.1:8080'
    $env:NO_PROXY    = 'localhost,127.0.0.1'

Обратите внимание: значение `HTTPS_PROXY` начинается с `http://`, потому что
это адрес прокси, а не схема целевого сайта. Соединение к прокси
в открытом виде, а HTTPS-сайт внутри через CONNECT.

curl также принимает `--proxy`, а доверие к CA задаётся через `--cacert`
или `-k` для отключения проверки:

    curl -v --proxy http://127.0.0.1:8080 --cacert D:\Projects\Librium\ca.crt https://example.com

Python `requests` берёт CA из переменной `REQUESTS_CA_BUNDLE`,
Node из `NODE_EXTRA_CA_CERTS`, Go из системного хранилища.

### Java

Не читает ни WinINET, ни переменные окружения. Только свойства JVM:

    java -Dhttp.proxyHost=127.0.0.1 -Dhttp.proxyPort=8080 ^
         -Dhttps.proxyHost=127.0.0.1 -Dhttps.proxyPort=8080 -jar app.jar

CA добавляется в keystore JVM через `keytool -importcert`.

### .NET

Классический .NET Framework читает WinINET. .NET Core и .NET 5+ читают
переменные окружения, а на Windows ещё и WinINET как запасной вариант.

### Программы, которые ничего не читают

Игровые клиенты, мессенджеры, часть мобильных эмуляторов. Для них
варианты: SOCKS5 если поддерживают, Proxifier (перехватывает Winsock
и заворачивает в SOCKS), файл hosts, WinDivert. Это темы для v2 и v3.

### Android и iOS

Эмулятор или телефон в той же Wi-Fi-сети: в настройках Wi-Fi указать прокси
`<IP компьютера>:8080`, а Librium должен слушать не только 127.0.0.1,
но и 0.0.0.0 или конкретный адрес интерфейса. CA ставится в настройках
устройства, на Android 7+ приложения по умолчанию не доверяют
пользовательским CA, нужен root или пересборка приложения.

## 6. Установка корневого сертификата Librium

Без этого HTTPS через прокси даст ошибку сертификата в каждом браузере.

**Хранилище Windows (для Chrome, Edge, curl со schannel, .NET):**

    certutil -addstore -user Root D:\Projects\Librium\ca.crt

Флаг `-user` ставит в хранилище текущего пользователя без прав администратора.
Без него в машинное, нужен запуск от администратора. Удалить:

    certutil -delstore -user Root "Librium CA"

Проверить: `certmgr.msc`, папка «Доверенные корневые центры сертификации».

**Firefox:** см. раздел 5.

**Меры безопасности.** Тот, у кого есть приватный ключ CA Librium, может
расшифровать любой HTTPS этого компьютера. Поэтому:

- ключ генерируется на каждой установке свой, не зашивается в программу;
- хранится в профиле пользователя с правами только для него;
- ставить CA лучше в отдельный профиль браузера, не в основной;
- удалять из хранилища, когда работа закончена.

## 7. Проверка: работает ли цепочка

Пошагово, от простого к сложному. Каждый шаг проверяет свой слой.

1. Прокси слушает порт:

       netstat -ano | findstr :8080

   Должна быть строка `TCP 127.0.0.1:8080 ... LISTENING` с PID Librium.

2. Прокси принимает CONNECT (без TLS-проверки):

       curl -v --proxy http://127.0.0.1:8080 -k https://example.com

   В выводе ищем `CONNECT example.com:443 HTTP/1.1` и ответ
   `200 Connection Established`. Дальше должен появиться TLS handshake
   и HTTP-ответ. Если тут ошибка, проблема в прокси.

3. CA установлен и подписывает правильно:

       curl -v --proxy http://127.0.0.1:8080 https://example.com

   То же без `-k`. Если ошибка `unable to get local issuer certificate`,
   curl не видит CA. Windows-сборка curl со schannel смотрит в хранилище
   Windows, сборка с OpenSSL требует `--cacert`.

4. Браузер:
   открыть https://example.com, нажать на замок, посмотреть цепочку.
   Издателем должен быть «Librium CA». Запрос должен появиться в истории
   прокси.

5. localhost через прокси:
   если тестируемое приложение локальное, проверить, что `<-loopback>`
   или соответствующая настройка Firefox выставлены, иначе запросы
   к 127.0.0.1 в прокси не попадут.

## 8. Что из этого должен уметь сам Librium

Минимум для v1:

- Слушать настраиваемый адрес, по умолчанию 127.0.0.1:8080.
- Генерировать CA при первом запуске и отдавать его по
  `http://127.0.0.1:8080/ca.crt`, как делают Burp (`http://burp`)
  и mitmproxy (`http://mitm.it`). Пользователь скачивает и ставит.
- Показывать в UI, какие приложения нужно настроить и как.

Удобства на потом:

- Кнопка «включить/выключить системный прокси» через реестр
  и `InternetSetOption`.
- Раздача PAC-файла с правилами по хостам из настроек scope.
- Кнопка «запустить изолированный Chrome» с нужными ключами
  и отдельным профилем, где CA уже установлен.
