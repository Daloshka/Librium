# Librium: как устроена отправка пакета и где возможен перехват

[← Назад к индексу](../README.md) · Связано: [Архитектура](architecture.md), [Настройка прокси](proxy-setup.md)

Дополнение к [архитектуре](architecture.md). Здесь про сеть в целом: слои, путь пакета
на Windows 10, детальная хронология HTTPS, а также UDP, ICMP, SMTP и другие
протоколы. Акцент первой версии на TCP и HTTPS, остальное для понимания
границ инструмента.

---

## 1. Слои: во что упакован HTTPS-запрос

Модель TCP/IP, снизу вверх. Каждый уровень оборачивает данные верхнего
в свой заголовок, это называется инкапсуляция. Определения каждого
протокола из таблицы: [Глоссарий протоколов](basics/protocols.md).

| Уровень      | Что это                      | Примеры                          | Адресация            |
|--------------|------------------------------|----------------------------------|----------------------|
| Канальный    | Доставка в пределах сегмента | Ethernet, Wi-Fi                  | MAC-адрес            |
| Сетевой      | Доставка между сетями        | IPv4, IPv6, ICMP                 | IP-адрес             |
| Транспортный | Доставка между программами   | TCP, UDP, QUIC (поверх UDP)      | Порт                 |
| Прикладной   | Смысл данных                 | HTTP, TLS, DNS, SMTP, WebSocket  | Зависит от протокола |

Один HTTPS-запрос в проводе выглядит так:

    [Ethernet-кадр
      [IP-пакет
        [TCP-сегмент
          [TLS-запись
            [HTTP-запрос: заголовки + тело]
          ]
        ]
      ]
    ]

Терминология: на IP-уровне это «пакет», на TCP «сегмент», на UDP «датаграмма»,
на Ethernet «кадр». В быту всё называют пакетами.

Важно для перехвата: HTTP-запрос не обязан помещаться в один пакет.
Большой ответ размазан по сотням TCP-сегментов, и собрать его обратно
в поток это работа TCP-стека, а не вашей программы. Прокси уровня приложения
(как Librium v1) получает уже собранный поток байтов и не видит пакетов вообще.

## 2. Путь пакета на Windows 10 от приложения до провода

Когда браузер вызывает отправку данных, происходит такая цепочка:

    Браузер (chrome.exe)
      |  send() / WSASend()  — Winsock API, ws2_32.dll
      v
    AFD.sys — Ancillary Function Driver, переводит вызовы Winsock в запросы ядра
      |
      v
    tcpip.sys — TCP/IP-стек ядра: собирает TCP-сегмент, IP-заголовок,
      |          управляет соединениями, повторами, окнами
      |
      +-- WFP — Windows Filtering Platform: точки фильтрации внутри стека,
      |         здесь стоят брандмауэр, антивирусы, WinDivert
      v
    NDIS — Network Driver Interface Specification: общий слой для сетевых карт
      |   здесь стоят NDIS-фильтры (Npcap для Wireshark)
      v
    Драйвер сетевой карты (miniport)
      v
    Провод / радио

Где можно перехватывать, от простого к сложному:

1. **Настройки прокси (уровень приложения).** Браузер сам отправляет всё
   на 127.0.0.1:8080. Ничего в системе не меняется. Работает только для
   программ, уважающих настройки прокси. Так работают Burp, Caido, mitmproxy
   по умолчанию. **Это Librium v1.**
2. **SOCKS5-прокси.** То же, но универсальнее: приложение просит прокси
   «подключи меня к host:port» для любого TCP, не только HTTP. Есть режим
   UDP ASSOCIATE для UDP. Требует поддержки со стороны приложения.
3. **Подмена DNS или файл hosts.** Направить домен на 127.0.0.1, где слушает
   ваш сервер. Грубо, но работает для приложений без настроек прокси.
4. **WFP callout-драйвер, например WinDivert.** Перехват на уровне ядра:
   можно забрать любой пакет, изменить, отбросить или перенаправить
   на свой порт. Так делают «прозрачные» прокси (Proxifier, Clash TUN-режим).
   Требует драйвер, права администратора, и надо самому обрабатывать TCP-
   поток либо перенаправлять соединение на локальный сервер.
5. **NDIS-фильтр (Npcap).** Пассивный снифер: видит кадры, но не может
   удобно вмешиваться. Так работает Wireshark. Для изучения незаменим.

Вывод для проекта: v1 живёт на уровне 1, дальше при желании добавляется 2,
уровень 4 это отдельная большая задача.

## 3. TCP: соединение как поток байтов

TCP даёт приложению иллюзию надёжного двустороннего потока байтов.
Под капотом:

**Соединение идентифицируется четвёркой:** IP источника, порт источника,
IP назначения, порт назначения. Порт источника браузер выбирает случайный
(например 51234), порт назначения известен: 443 для HTTPS.

**Установление, three-way handshake** (подробно в
[TCP handshake](basics/tcp-handshake.md)):

    Клиент -> Сервер:  SYN        (seq=x)          «хочу соединение»
    Сервер -> Клиент:  SYN, ACK   (seq=y, ack=x+1) «согласен, подтверждаю»
    Клиент -> Сервер:  ACK        (ack=y+1)        «подтверждаю, начинаем»

Только после этого могут идти данные. Один RTT (round-trip) потрачен
ещё до первого байта TLS.

**Передача:** данные режутся на сегменты (обычно до 1460 байт полезной
нагрузки при MTU 1500). Каждый байт нумеруется (sequence number), получатель
подтверждает (ACK). Потерянные сегменты отправляются повторно. Окно (window)
ограничивает, сколько байт можно отправить без подтверждения.

**Закрытие:** обмен FIN/ACK в обе стороны, либо RST при обрыве.

**Что это значит для прокси:** прокси уровня приложения работает с двумя
TCP-соединениями: браузер<->прокси и прокси<->сервер. Это независимые
соединения с разными четвёрками. Сервер видит IP прокси, а не браузера.
Пакеты, сегменты, SYN и ACK прокси не видит и не должен: их обрабатывает
tcpip.sys.

## 4. HTTPS: полная хронология одного запроса

Пример: браузер открывает https://example.com/ напрямую, без прокси.

### 4.1. DNS

Браузер не знает IP example.com. Он отправляет DNS-запрос:

- Классический DNS: UDP, порт 53, к резолверу из настроек сети. Открытым
  текстом. Ответ: A-запись с IPv4 и/или AAAA с IPv6.
- Современные браузеры могут использовать DoH (DNS over HTTPS, TCP 443)
  или DoT (DNS over TLS, TCP 853). Тогда запрос зашифрован.

Кэш: сначала проверяется кэш браузера, потом кэш Windows (ipconfig /displaydns),
потом файл hosts, потом сетевой запрос.

### 4.2. TCP handshake к IP:443

Три сегмента из раздела 3. Данных ещё нет.

### 4.3. TLS handshake (версия 1.3, сегодня основная)

TLS работает записями (records). Каждая запись имеет 5-байтный заголовок:
тип (1 байт), версия (2 байта), длина (2 байта), затем до 16 КБ данных.
Типы: handshake (22), application_data (23), alert (21), change_cipher_spec (20).

    Клиент -> Сервер:  ClientHello
       - поддерживаемые версии TLS
       - список cipher suites (наборов алгоритмов)
       - random (32 байта)
       - расширение SNI: имя хоста «example.com» ОТКРЫТЫМ ТЕКСТОМ
       - расширение ALPN: список протоколов «h2», «http/1.1»
       - расширение key_share: публичный ключ клиента для обмена (X25519)

    Сервер -> Клиент:  ServerHello
       - выбранная версия и cipher suite
       - random сервера
       - key_share сервера
       > с этого момента обе стороны вычисляют общий секрет (ECDHE)
         и ВСЁ дальнейшее шифруется

    Сервер -> Клиент (зашифровано):
       EncryptedExtensions  - в том числе выбранный ALPN, например «h2»
       Certificate          - цепочка сертификатов сервера
       CertificateVerify    - подпись приватным ключом сервера,
                              доказывает владение сертификатом
       Finished             - MAC всего рукопожатия

    Клиент проверяет цепочку: сертификат example.com подписан
    промежуточным CA, тот подписан корневым CA, корневой лежит
    в доверенном хранилище ОС или браузера. Проверяет, что имя в сертификате
    совпадает с запрошенным хостом, срок не истёк, сертификат не отозван.

    Клиент -> Сервер (зашифровано):  Finished

Итого один RTT на TLS 1.3 (в TLS 1.2 было два). После этого идут записи
типа application_data, внутри них HTTP.

Что видно снаружи в зашифрованном соединении: IP-адреса, порты, SNI
(имя хоста), ALPN, размеры и тайминги записей. Не видно: URL-путь,
заголовки, тело, куки.

### 4.4. HTTP внутри TLS

Если по ALPN договорились о «h2», внутри идёт HTTP/2: бинарные кадры (frames),
несколько запросов одновременно в одном соединении (streams), заголовки
сжаты HPACK. Если «http/1.1», внутри идёт текст:

    GET / HTTP/1.1\r\n
    Host: example.com\r\n
    User-Agent: ...\r\n
    \r\n

Ответ приходит теми же записями application_data. Соединение остаётся
открытым (keep-alive) и переиспользуется для следующих запросов к этому хосту.

### 4.5. Та же хронология, но через прокси Librium

Браузер настроен на прокси 127.0.0.1:8080. Меняется всё:

1. **DNS браузер не делает.** Он не знает и не должен знать IP example.com,
   резолвить будет прокси.
2. TCP handshake к **127.0.0.1:8080**, не к серверу.
3. Открытым текстом: `CONNECT example.com:443 HTTP/1.1` плюс заголовок Host.
   Прокси отвечает `HTTP/1.1 200 Connection Established\r\n\r\n`.
4. Браузер начинает TLS handshake, шлёт ClientHello **прокси**.
   Прокси читает SNI (или берёт хост из CONNECT), достаёт из кэша либо
   генерирует через rcgen сертификат на example.com, подписанный CA Librium,
   и отвечает ServerHello с ним. Браузер принимает, потому что CA Librium
   в доверенном хранилище.
5. Параллельно прокси: DNS-запрос example.com, TCP handshake к настоящему
   IP:443, свой TLS handshake как клиент через rustls, с проверкой настоящей
   цепочки (либо без проверки, если пользователь так настроил).
6. Теперь у прокси два расшифрованных потока. Он читает HTTP-запрос из
   первого, сохраняет сырые байты, при включённом Intercept ждёт решения
   пользователя, затем пишет во второй. Ответ в обратную сторону.

Про ALPN: прокси должен договориться с браузером о том же протоколе,
что с сервером, либо принудительно предлагать браузеру только http/1.1.
Для v1 проще всего второй вариант: тогда внутри всегда текстовый HTTP/1.1,
а HTTP/2 к серверу добавляется позже.

### 4.6. Что ломает MITM

- **Certificate pinning.** Приложение (часто мобильное) сравнивает сертификат
  с зашитым и отвергает подмену. Обходится только модификацией приложения.
- **HSTS + preload.** Не мешает MITM с доверенным CA, но не даёт
  «кликнуть мимо» предупреждения, если CA не установлен.
- **Client certificates (mTLS).** Сервер требует сертификат клиента;
  прокси должен уметь его подставлять.
- **QUIC / HTTP/3.** См. раздел 5. Chrome при настроенном HTTP-прокси
  QUIC не использует и падает на TCP, это спасает прокси.
- **Encrypted ClientHello (ECH).** Прячет SNI. Для явного прокси не проблема,
  хост известен из CONNECT.

## 5. UDP

Датаграммы без соединения: нет handshake, нет подтверждений, нет порядка,
нет повторов. Каждая датаграмма независима, до ~64 КБ, на практике меньше MTU.
Заголовок 8 байт: порты источника и назначения, длина, контрольная сумма.

Кто использует:

- **DNS** (порт 53), самый частый UDP-трафик.
- **QUIC / HTTP/3** (порт 443 UDP). Google, Cloudflare, YouTube. QUIC сам
  реализует надёжность и шифрование поверх UDP, причём шифрует даже
  большую часть handshake. TLS 1.3 встроен внутрь.
- **DHCP, NTP, SNMP, VPN (WireGuard, OpenVPN UDP), игры, VoIP, видеозвонки.**

Перехват UDP:

- Через настройки HTTP-прокси невозможен, протокол HTTP-прокси знает
  только TCP.
- Через SOCKS5 возможен командой UDP ASSOCIATE, но мало кто это поддерживает.
- Реально только через WinDivert или TUN-интерфейс, где вы видите датаграммы.

Для веб-тестирования UDP в v1 не нужен: с прокси браузеры сами уходят
с HTTP/3 на TCP. Если в будущем захочется HTTP/3, потребуется QUIC-стек
(quinn на Rust) и прозрачный перехват.

## 6. ICMP и ping

ICMP не транспортный протокол, у него нет портов, он живёт прямо поверх IP.
Служебные сообщения: «хост недостижим», «время жизни истекло» (traceroute),
«эхо-запрос» и «эхо-ответ» (ping).

Ping: отправляется ICMP Echo Request с идентификатором, номером и произвольной
полезной нагрузкой, узел отвечает Echo Reply с той же нагрузкой. Измеряется
время туда-обратно.

Для прокси приложений ICMP не существует: без портов и соединений его нельзя
направить в прокси. Увидеть можно только сниффером или WinDivert.
Для безопасности интересен как канал утечки (ICMP-туннели), но это
за пределами Librium.

## 7. SMTP и другие протоколы поверх TCP

Большинство старых прикладных протоколов это текстовые диалоги поверх TCP.

**SMTP** (отправка почты), порты 25, 587, 465:

    S: 220 mail.example.com ESMTP
    C: EHLO client.local
    S: 250-mail.example.com
    S: 250 STARTTLS
    C: STARTTLS
    S: 220 Go ahead
    > дальше TLS handshake внутри того же TCP-соединения, потом
      MAIL FROM, RCPT TO, DATA уже зашифрованы

Два способа TLS, важно различать:

- **Implicit TLS:** соединение сразу начинается с TLS (HTTPS 443, SMTPS 465,
  IMAPS 993). Прокси делает MITM с первого байта.
- **STARTTLS:** сначала открытый текст, потом команда апгрейда (SMTP 587,
  IMAP 143, LDAP 389, PostgreSQL). Прокси обязан понимать протокол, чтобы
  поймать момент апгрейда и вклиниться в TLS.

Похожие: **IMAP/POP3** (почта), **FTP** (отдельные соединения для команд
и данных, неудобен для прокси), **SSH** (свой протокол шифрования,
не TLS, MITM только с подменой ключа хоста, клиент это заметит),
**MySQL/PostgreSQL** (бинарные протоколы со своим STARTTLS-подобным апгрейдом).

Протоколы поверх HTTP, которые прокси увидит бесплатно после MITM:
**WebSocket** (начинается как HTTP-запрос с Upgrade, потом двусторонние
кадры внутри того же соединения), **gRPC** (HTTP/2 + protobuf),
**GraphQL, REST, SOAP** (просто HTTP).

Как перехватить произвольный TCP-протокол: приложение должно уметь SOCKS5,
либо нужен WinDivert. Дальше прокси либо слепо туннелирует байты и логирует
их, либо знает протокол и разбирает его. Caido и Burp умеют только HTTP,
WebSocket и «сырой» TCP-туннель.

## 8. Где Librium в этой картине

    v1  явный HTTP-прокси (CONNECT + MITM), TCP только, HTTP/1.1 внутри TLS,
        WebSocket как бонус
    v2  HTTP/2 к серверу и клиенту, SOCKS5 для произвольного TCP
    v3  прозрачный режим через WinDivert, тогда UDP/QUIC становятся достижимы

## 9. Как увидеть это своими глазами

- **Wireshark** с Npcap: фильтр `tcp.port == 443` покажет handshake, ClientHello
  с SNI, затем зашифрованные записи. Фильтр `dns` покажет резолв.
  Переменная окружения SSLKEYLOGFILE заставит Chrome/Firefox писать
  сессионные ключи, и Wireshark расшифрует TLS без всякого MITM.
- `netstat -ano` покажет TCP-соединения и их четвёрки, с PID процесса.
- `curl -v https://example.com` покажет TLS handshake и HTTP текстом.
- `curl -v --proxy http://127.0.0.1:8080 https://example.com` покажет CONNECT
  и дальше то же, как это будет выглядеть через Librium.
- `openssl s_client -connect example.com:443 -servername example.com`
  покажет цепочку сертификатов и параметры TLS.
